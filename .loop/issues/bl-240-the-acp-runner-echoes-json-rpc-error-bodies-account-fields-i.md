The acp runner emits every stdout line of the agent as a RunnerEvent.Output before it decodes the frame (AcpRunner.kt, the ProcessEvent.Line branch). The orchestrator redacts only known secrets in those lines, so a JSON-RPC error whose data carries a Google error body, for example the metadata of an exhausted Gemini quota, can bring an account id or an email into the attempt's runner output and its record file. bl-215 keeps them out of the rate_limit event and the turn_failed reason it adds, but did not change the raw echo, which applies to every protocol line. Worth deciding whether error frames (or their data) should be redacted or left out of runner output, and whether the same holds for the other runners.

Follow up of bl-215 (default:bl-215), filed by Loop from attempt 12027e80-73d8-4f2f-b8bb-edcdb6eab7e7.

## Agent Brief

**Category:** enhancement
**Summary:** keep the `data` of JSON-RPC error responses out of runner output in the acp and codex-app-server runners, and check the claude-code runner for the same case.

**Current behavior:** each protocol line is echoed raw as runner output, so the `data` of an error response (for example the Google error body of an exhausted Gemini quota, with account fields) is stored and shown in full.

**Desired behavior:**
- For a stdout line that decodes as a JSON-RPC error response, the acp runner echoes a rewritten line that keeps `jsonrpc`, `id`, `error.code` and `error.message` and replaces `error.data` with a marker such as `"[error data omitted, N chars]"`. Every other line is echoed unchanged. A line that does not decode is echoed unchanged, as today.
- The decoded frame used by the runner keeps the full `data`, so bl-215's rate limit parsing (`rate_limit` event, the `turn_failed` reason) works as before.
- The codex-app-server runner applies the same rule to its JSON-RPC error responses. Share the rewrite if both runners can use one helper without a new module dependency; otherwise keep one small function per runner.
- Check whether the claude-code runner's stream-json output can carry provider error bodies with account fields (an error `result` or an API error event). If it can, apply the equivalent rule there; if not, say so in `docs/spec-decisions.md`.

**Key interfaces:**
- `AcpRunner.kt`, the `ProcessEvent.Line` branch and the queued line echo; `AcpFraming.kt` for decoding.
- `CodexAppServerRunner.kt`, the `ProcessEvent.Line` branch and the queued line echo.
- `ClaudeCodeRunner.kt`, the line echo around line 823.

## Acceptance criteria

- [ ] A test per runner (acp, codex-app-server) feeds a JSON-RPC error response whose `error.data` holds an email and an account id, and asserts no `RunnerEvent.Output` contains either value, while `code` and `message` are present in the echoed line.
- [ ] The acp test also asserts the `rate_limit` event and the `turn_failed` reason added by bl-215 are still produced from the same frame.
- [ ] A test asserts a non error line and an undecodable line are echoed byte for byte unchanged.
- [ ] The claude-code runner is either covered by an equivalent test or `docs/spec-decisions.md` records why it does not need one.
- [ ] `docs/spec-decisions.md` records the rule (error data is omitted from runner output, the decoded frame keeps it).
- [ ] `./gradlew build` passes.

## Out of scope

- A general email or account id pattern in `SecretRedactor` (it would touch every writer, git output included).
- Changing what the store, `loop show` or the exporters do with runner output.
- Any change to bl-215's rate limit telemetry beyond keeping it working.
