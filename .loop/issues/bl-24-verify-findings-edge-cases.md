## Agent brief

**Category:** bug

**Summary:** Close seven low findings of verification: findings for a long single line of output, a refutation overtaken by the agent's own handoff on a sessionless runner, stale findings, the trace header of a refuted attempt, a check event cut by a cancel, the evidence view falling back silently, and a fingerprint doc that says more than the code does.

**Current behavior:**
- When a failed check's output is longer than 64 KiB and its last 64 KiB hold no newline (one long minified line), the findings sent to the agent say "Its output was empty."
- The KDoc of the findings says the output is redacted before it is cut. The code cuts to the last 64 KiB first, then redacts.
- With a runner that has no session, an attempt whose drain holds a refuted move and then an applied move to another state (for example `needs_info`) ends as failed with the reason `refuted`. It counts against `retries.max_attempts` and can park an issue that is waiting for an answer. Only third party runners are sessionless.
- The findings kept for the next attempt of an issue are cleared only when that next attempt renders its prompt. When the issue leaves the active states first, or its workspace is removed, they stay and reach a much later attempt.
- The `loop trace` header of an attempt that ended `failed` with the reason `refuted` or `unverified` shows no reason.
- A cancel that arrives while a check's evidence is being saved leaves a `check_started` event with no `check_finished`, and an evidence file no event names.
- `loop show <attempt> --evidence` prints the evidence of an older check run when the latest run saved none, without saying so.
- The fingerprint's KDoc and the spec decisions doc say staging changes nothing. Staging a new file changes the value, because the file moves from the untracked hash to the diff hash. The diff the fingerprint hashes may also depend on the repository's git config (index line length, context lines, prefixes, diff algorithm).

**Desired behavior:**
- Findings for an output whose tail has no newline show the end of that line, cut like any other line. "Its output was empty." is said only for an output with no non blank line. Outputs under 64 KiB and outputs with newlines read as today.
- The KDoc states the real order (cut to the tail, redact, then cut to lines) and why it is safe.
- On the sessionless path, a refutation followed in the same drain by a move that was applied does not end the attempt as `refuted`: the attempt ends as it would have without the refutation. A refutation with no later applied move ends as today.
- The findings kept for an issue are dropped when the issue leaves the active states (handoff, terminal or not found) and when its workspace is removed. A park keeps them, so a resumed issue still gets them.
- The trace header prints the reason after the duration for `refuted` and `unverified`, in the same form as the other reasons.
- Every `check_started` is followed by a `check_finished`, also when a cancel arrives during the evidence save: either the save completes and the event names the file, or the event records the cancel. No evidence file is left that no event names. The KDoc of the check run lists its steps in the order the code runs them.
- `loop show --evidence` prints the evidence of the latest run of the check (or of the latest check run without `--check`). When that run has no evidence file it says so and prints nothing older.
- The fingerprint doc says what the code does: staging a change to a tracked file changes nothing, staging a new file changes the value. The value of one work tree state does not change when `core.abbrev` or the diff presentation settings of the repository config change. The value of a clean tree stays what it is today, so `WorkspaceFingerprint.EMPTY_HASH` and `committedHead` are untouched.

**Key interfaces:**
- `VerifyFindings.of` and its tail reading.
- The attempt's turn loop in the orchestrator, its sessionless branch and the function that ends an attempt as refuted, the per issue findings the orchestrator keeps for `loop.verify_findings`.
- The orchestrator's check run and its evidence save, `EvidenceWriter`, the events `check_started` and `check_finished` and their `canceled` and `evidence` fields.
- The `loop trace` header reason, the `loop show --evidence` view.
- `WorkspaceFingerprinter` and the diff options it passes through `WorkspaceGit`.

**Out of scope:**
- Keeping findings across a process restart.
- Memory use of a check at the 16 MiB output cap, pruning evidence files, the file mode of untracked files.
- Making the fingerprint blind to staging a new file.

**Triage notes:**
- Findings are dropped when the issue leaves the active states and kept on a park.
- For staging a new file, the doc is corrected and the code stays. Making the value blind to staging costs more and buys nothing for the clean tree comparisons that decide deliveries.
- The config dependence of the diff hash was reasoned from git's behavior, not run. The fingerprint test settles it: if it passes before any change, the agent says so and changes nothing there.
