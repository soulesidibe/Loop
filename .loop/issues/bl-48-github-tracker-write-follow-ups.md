## What

Found in the Fable 5.2 recheck of #65 (m2-23) and by the m2-23 agent on 2026-11-13. All low.

What is known:

- A handoff plus a terminal read skips workspace cleanup. `RetryCoordinator.kt` (around line 315) drops the entry on `summary.handedOff` whatever the exit reason. If the issue reads terminal at the refresh right after the attempt's move (a human or automation closes it in that window), no continuation retry exists, so `onTerminalRetryDropped` never runs and the workspace stays until the next startup cleanup. The same early drop resets counters on `not_found`, which the comment just below says is kept on purpose. Restricting the drop to `not_active` and `no_continuation` exits fixes both. It applies to the files tracker too, but the window is milliseconds.
- Reload race on the required labels. `RunCommand.kt` (around line 277) sets the `AtomicReference` inside the `reloadWarnings` callback, which `Orchestrator.kt` (around line 856) calls after `effective = reloaded` and a suspending sink write. A move drained in that window removes the old required labels; if the labels were renamed, the issue stays eligible under the new workflow and is dispatched again while carrying `needs-review`. Hiding a state update in a callback named for warnings is also fragile.
- Comment count over bump (`GitHubTracker.kt`, around line 205). If a concurrent read already counted the new comment, the bump adds one more. At exactly 100 comments this asks for an empty page 2 and shows no comments until the next read. A POST that times out after GitHub applied it leads to a duplicate comment on retry.
- An oversized comment queued with a handoff is lost to the agent: it is refused at the drain, the move applies and the attempt ends. The refusal lands only in `tool_request_failed`, and the reviewer sees no comment. A length check in `loop tool comment` (and the MCP `comment`, see bl-45) would refuse it at once.
- Docs: a reload of `handoff_labels` needs a restart, and the warning (`Host.kt`, around line 278) reads "tracker.provider changed to o/r, Loop keeps reading o/r", which misleads. The profile mentions only the `required_labels` reload.
- Seen by the m2-23 agent: `loop trace` looks an issue up by id, so on GitHub it takes the number (`loop trace 26`), not the identifier. Documented in the profile's known gaps.
- Test gaps: the comment count refresh is proven at tracker level only, not through a dispatch; `tool_request_failed` is proven end to end for 403 only.

## Agent brief

**Category:** bug

**Summary:** Close four low findings of the GitHub tracker write side: cleanup after a handoff that reads terminal, the order of a required labels reload, the comment count after a write, and the wording of a provider reload warning.

**Current behavior:**
- When an attempt hands off (its own move to a handoff state) and the issue reads terminal at the refresh right after, the retry entry is dropped at once with the counters reset. No continuation retry exists, so the terminal cleanup of the workspace never runs and the workspace stays until the next startup cleanup. The same early drop resets the counters when the issue reads not found, although not found is meant to keep them.
- On a reload of `tracker.required_labels`, the orchestrator switches to the new workflow, writes `config_reloaded`, and only then the tracker learns the new labels, through a callback named for warnings. A move drained in between removes the old required labels.
- After a comment write the tracker adds one to the comment count it holds. When a read already counted that comment, the count is one too high. At exactly 100 comments the next completion asks for an empty second page and shows no comments until the next list read.
- A reload that changes only a provider setting of the same repository, such as `handoff_labels`, warns "tracker.provider changed to owner/repo, Loop keeps reading owner/repo until loop run is restarted", which names the same repository twice and does not say what changed. The adapter profile says only that a `required_labels` reload is live.

**Desired behavior:**
- After a handoff, the early drop with the counters reset applies only when the attempt ended because the issue left the active set by that handoff (`not_active`) or because the runner ran its one turn (`no_continuation`). A handoff followed by a terminal read ends like any terminal exit: the workspace is removed as for a terminal issue. A handoff followed by not found keeps the counters, like any not found exit. Both trackers behave the same.
- The labels a handoff move removes are always those of the workflow the orchestrator has in effect when the move is applied. No window exists in which the orchestrator is on the new workflow and the tracker on the old labels. The callback for reload warnings only returns warnings.
- After a comment write, the next completion shows the new comment and never asks for a page past the last one, whether or not a read already counted the comment. One way: forget the held count for that issue so the next completion reads without a page hint, or cap it by what the last read reported. The agent chooses, the behaviour is what counts.
- A reload that changes provider settings of the same repository warns with the setting that changed and that it needs a restart, for example `tracker.provider.handoff_labels changed, Loop keeps the previous value until loop run is restarted`. The token is never printed. The adapter profile says which github provider settings are live on reload (`required_labels`) and which need a restart.

**Key interfaces:**
- `RetryCoordinator`, its handling of `AttemptSummary.handedOff` on a succeeded attempt, `ExitReason.NOT_ACTIVE`, `ExitReason.NO_CONTINUATION`, `ExitReason.TERMINAL`, `ExitReason.NOT_FOUND`, and the `onTerminalRetryDropped` callback.
- The `requiredLabels: () -> List<String>` parameter of `GitHubTracker` and of `trackerFor`, and how `loop run` feeds it. The orchestrator's `reloadWarnings: (WorkflowFile, WorkflowFile) -> List<String>` parameter.
- `GitHubTracker.addComment`, `GitHubTracker.completeIssue` and the comment counts they share.
- The function that builds reload warnings for a changed tracker (`reloadWarnings` of the host), `GitHubTrackerSettings`.

**Out of scope:**
- Partial label moves and the rate limit between the add and a removal (bl-47).
- A comment size check at call time (bl-45).
- `loop trace` by identifier on GitHub.
- Making `handoff_labels` reload live.
