## Agent brief

**Category:** bug

**Summary:** The human log and `check_finished` say a check failed when it could not run, and count a rerun as a second check.

**Current behavior:**
For a visible check that exits 126 or 127, times out or ends without an exit code, `check_finished` carries no `reason` (only a start error sets it), and the human log prints "check <command> failed with exit code 127". The verdict that follows says the check could not run. The verdict line of the human log counts evidence files, so one check that failed and passed on its rerun prints "evidence of 2 checks saved". The KDoc of `ParkReason.Unverified` says "It is not a failure" although the attempt that parks ends failed.

**Desired behavior:**
- `check_finished` of a visible check carries `reason` whenever `CheckResult.couldNotRun` is not null, redacted and cut like the start error reason today. A holdout's event is unchanged: `result` only.
- The human log line of such a check reads "check <command> could not run: <reason>", for a first run and a rerun alike. A check that ran and failed keeps "failed with exit code <n>". A timeout keeps its own wording or uses the reason, as long as it never says "failed".
- The verdict line counts distinct checks with saved evidence, so a fail then pass check reads "evidence of 1 check saved".
- The KDoc of `ParkReason.Unverified` says what is true: the park takes no `max_attempts` slot, and the attempt itself ends failed.
- `loop trace` shows the new `reason` like any other event field.

**Key interfaces:**
- `CheckResult.couldNotRun`: already holds the sentence, reuse it as the event's `reason`.
- The `check_finished` event written by the orchestrator's check run.
- `HumanLog` check line and verdict line.
- `ParkReason.Unverified`.

**Out of scope:**
- Any change to which results count as could not run (126, 127, 137).
- A dispatch time skip or a preflight refusal for `checks: []`.
- A new `loop show` option for the first run's evidence.
- The park and cancel races named in the issue.

**Triage notes:**
- Trimmed to the wording, evidence count, KDoc and test gaps. All four are still true on main.
- Kept as notes, not in scope: first run evidence in `loop show` (needs a small CLI decision, low value, the first run's file exists on disk and `loop show --events` names it).
- Kept as an open question for the maintainer: `checks: []` runs a full attempt before the park. The docs call it valid on purpose. Should a kind with `checks: []`, no holdout and no `acceptance_commands` be refused at preflight, or skipped at dispatch with a recorded skip?
- Kept as notes: the two plausible races (park written after close and `after_run`, cancel during `parkNow`). Not reproduced, and both fail toward running checks again, never toward delivery.
- Wontfix: exit 137 counts as ran and failed and 126 parks, this is the documented "could not run" rule.
