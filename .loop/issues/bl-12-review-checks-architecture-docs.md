## What

As planned, the review in a verify contract (plan 6.4, reviewer in M6) grades each acceptance criterion from the deliverable and the evidence. It does not check that the change follows the project's documented decisions: `AGENTS.md`, `CONTEXT.md`, `docs/adr/`. Criteria can all pass while the code ignores an ADR or the glossary. Guards catch weakened tests and protected paths, not that kind of drift.

Outside reference: Shopify's Helix (shopify.engineering/helix, 2026-09-21) and its app rebuild (shopify.engineering/shopify-app-rebuild, 2026-11-10) run reviewers whose only job is conformance to the documented architecture. Two reviewers in fresh, separate contexts check the code and loop until both approve. Humans review last.

Proposed shape, to settle in triage:

- A conformance part of the review that reads the docs the kind declares, for example `review: { docs: [AGENTS.md, CONTEXT.md, docs/adr/] }`.
- Each finding cites a doc and the line or section it breaks.
- A conformance finding refutes the verdict like a failed check, and is sent back as continuation guidance (`loop.verify_findings`).
- The reviewer gets a fresh context: the docs, the diff and the evidence, never the worker's transcript.

## Questions for triage

- Does conformance belong in the M6 reviewer, or should a minimal version come earlier (for example a `command` check that runs a reviewer script) since review is where Shopify reports the most value?
- One reviewer or two isolated ones? The plan already has a council in M7.
- How are the declared docs budgeted in the reviewer's prompt (plan 8.5), given ADRs grow over time?
- Can a conformance finding be wrong enough to need a human override, and how does that fit "a failed check is never overridden"?
