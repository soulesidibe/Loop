## What

`startApprovalWait` (Orchestrator.kt, around line 794) saves the new approval wait and then sends the human notice (the channel, the `human_notified` sink write, and `hooks.on_human_needed` up to its timeout). All of this runs inside `waitingFor` (around line 4343), whose `finally` decides what to do with the verify wait it held:

```kotlin
when {
    waits.awaitsApproval(wait.issueId) -> Unit
    end -> withContext(NonCancellable) { endWaiting(wait) }
    else -> waits.forget(wait.issueId)
}
```

If the human runs `loop send-back` during the notice, and a poll runs in that window, `Waits.read` sees the stored row is a sent back approval and releases the hold. When the notice returns, `awaitsApproval` is false, so the `finally` calls `endWaiting`, an unconditional delete of the wait row. The send back row is gone.

Effect, reproduced: the reason is lost and the issue dispatches again as a fresh attempt instead of a sent back one. The CLI already printed "Sent back" and commented. Nothing merges or moves. The comment around line 800 says the save is safe; it is, but the end in `waitingFor` is not.

## Agent brief

Make the `finally` of `waitingFor` never delete a row a human decided:

- Keep the wait when `waits.sentBack(wait.issueId) != null` (the stored row is a sent back approval). Leave it to the dispatch path that already handles a sent back wait.
- Or end the verify wait only if the store still holds the verify row: use the conditional write bl-250 added (`replaceApproval` or its sibling) so the delete compares the stored row and keeps a different one. Prefer this if bl-250's primitive fits, since it also covers an approve that lands in the window.
- Do not change what happens on cancellation (`endOnCancel`) or when no human acted.

Write a deterministic test with a hook, in the style of bl-224's `duringCommentRead` and bl-250's `afterRead` hooks, never a sleep: block inside the notice (for example on the `human_notified` sink write or a fake channel), commit a `loop send-back` through the real store, run a second tick so `Waits.read` releases the hold, then release the notice. First show the test fails on main (the row is null afterwards), then make it pass.
