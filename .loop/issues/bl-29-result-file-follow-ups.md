## Agent brief

**Category:** bug

**Summary:** Never follow a symlinked `.loop` folder for the result file, never move to `needs_info` without the question, and tighten the result parser.

**Current behavior:**
With `.loop` a symlink to a folder outside the workspace, Loop reads the result file there, saves it as evidence and deletes it outside the workspace. The check on the result file refuses a symlink for the last path component only. A `needs_info` result applies its comment and its move independently, so the issue can reach `needs_info` with no question when the comment fails. The comment carries the whole summary, up to 1 MiB. A result file that starts with a UTF-8 byte order mark is `invalid_result`. `followups` and `residual_human_steps` accept elements of any type.

**Desired behavior:**
- `ResultFile.take` and `ResultFile.discard` refuse a result path whose `.loop` component is a symlink or not a folder. `take` returns an invalid result with a message such as `.loop is a symlink`, and nothing outside the workspace is read or deleted. `discard` removes nothing outside the workspace and reports the stale file as it does today for one it cannot remove.
- For `needs_info`, the move is applied only when the comment was applied. When the comment fails, `tool_request_failed` is recorded for the comment as today, the move is not attempted, and the agent is told in the next turn's guidance like any failed request.
- The comment of a `needs_info` result is cut to a fixed bound of 65,536 characters, with a closing line that says it was cut. The full text stays in the saved result beside the evidence.
- A leading byte order mark is ignored by `SubmittedResult.parse`.
- `followups` and `residual_human_steps` must be lists of strings, else the result is invalid with a message naming the key.

**Key interfaces:**
- `ResultFile.take`, `ResultFile.discard`.
- The orchestrator's handling of `SubmittedResult.Status.NeedsInfo`.
- `SubmittedResult.parse`.

**Out of scope:**
- The fixed `review` target and any new config key for it.
- Mixed drains of queued requests and a result.
- Duplicate JSON keys.
- The comment size of `loop tool comment` and of the MCP `comment` tool (bl-45), unless the same constant is reused.

**Triage notes:**
- Trimmed to the symlinked folder, the `needs_info` order and cap, and the parser. The comment cap is 65,536 characters, the same number as bl-45.
- Left open, not in scope, each needs a maintainer decision. First, the handoff state of a `done` result is the constant `review`. Question: should it be a config key of the kind, or stay `review` with a preflight check on the files tracker that the state is neither active nor terminal (the bl-46 rule)? The second is cheap and consistent. Second, mixed drains: when one drain holds both a queued tracker request and a submitted result, which wins? A simple rule: a submitted result is the only thing applied in its drain, and queued moves in the same drain are recorded as dropped.
- Wontfix: a failed delete of the result file failing the attempt, then `invalid_result` on each retry. It fails closed by design (the KDoc says "never taken twice in silence"). Worth one test only.
- Wontfix: duplicate JSON keys, detecting them needs a custom parser for no real gain.
- Wontfix: an `after_run` hook writing a result file, hooks are trusted (spec 15.4).
