## Agent brief

**Category:** bug

**Summary:** Bound and clean the agent chosen target of a failed request everywhere it is recorded.

**Current behavior:**
The one line rule of the failed request notice replaces ASCII controls and whitespace only (the pattern is ASCII only without the Unicode flag), so C1 controls, a no break space and bidi overrides pass. The restored wait path records `tool_request_failed` and `result_submitted` with an unredacted `to`, while the live path redacts it. The event's `to` is unbounded and may hold line breaks. A queued request file of any size is read fully into memory.

**Desired behavior:**
- The one line rule also replaces Unicode control and format characters and Unicode spaces (categories Cc, Cf, Zs, Zl, Zp), so bidi overrides and C1 controls never reach the notice. A target that is empty after that reads `move to (empty)`. A cut never splits a surrogate pair.
- Every `tool_request_failed` and `result_submitted` event redacts `to`, the restored wait path included.
- The `to` of those events is put on one line and cut to a fixed bound of 256 characters.
- `ToolRequestQueue` treats a request file larger than 1 MiB plus a small margin as unreadable, with a reason that says it is too large, without reading it whole. The existing 1 MiB bound of a submitted result still fits.

**Key interfaces:**
- The orchestrator's failed request recording and its notice helpers (`failedRequestName`, the one line helper).
- The restored wait verification path.
- `ToolRequestQueue.pending` and `QueuedRequest.Unreadable`.

**Out of scope:**
- The rule that keeps the first reason for two failed moves to one state.
- Comment size limits (bl-45, bl-29).

**Triage notes:**
- Small. All three findings confirmed on main. Nothing here reaches a wrong outcome, so it is a hardening issue.
