## Parent

## What

`agent.max_concurrent_agents` is meant to cap agent attempts and merge checks (bl-180's docs). In practice it does not cap verification builds:

1. **A lowered cap.** With the cap raised to 3, three attempts (bl-96, bl-152, bl-107) reached verification within 10 minutes. Each ran `./gradlew --no-daemon build` at the same time; each took 29 to 31 minutes instead of about 13 and failed on load flakes (`RunCommandTest > SIGINT…`, `RestartStateTest`, `WorktreeHooksTest`, `CodexRotationRunTest`). Lowering the cap to 1 (reloaded at 17:20) only limits new attempts; the three running attempts kept their slots.
2. **A resubmit.** When the operator killed one verification build (bl-96), the attempt's agent got a turn, resubmitted in 90 seconds, and verified again at once, in parallel with the others, since the attempt still held its slot.
3. **A restart.** `loop stop` then `loop run` restored three `verify` waits and one `merge` wait (m4-06, approved) and resumed all four at the same tick (17:56:11), so four Gradle builds ran at once with the cap at 1. Load average reached 130.

Desired: at most `max_concurrent_agents` verification and merge check builds run at once in every case: after a reload that lowers the cap, on a resubmit, and when a restart resumes stored waits. Excess ones queue (oldest first) instead of starting. Triage decides whether verification needs its own cap (for example `verification.max_concurrent`, default 1) separate from agent turns, since agent turns are mostly model time and run well in parallel while builds do not.

Related: bl-07 (stalls under test load), bl-57 (parallel test flakes), bl-180 (the slot rules of the merge phase), bl-186.

Area: the orchestrator's slot accounting (grep `Orchestrator.kt`, never read it whole), the verify and merge waits, restart recovery.

Bug, ready-for-agent, priority 2. The premise holds in the code. `SlotUse` and `SlotPlan.hasFreeSlot` (`spec-core/src/main/kotlin/loop/core/orchestrator/SlotPlan.kt`) count only running attempts and phase `check` merge checks, and the KDoc says a restored wait's checks take no slot. `restoreWaiting` and `resumeWait` in `Orchestrator.kt` start every stored `verify` rerun with `scope.async` and ask no slot plan at all. An attempt's own verification (`waitingFor { verification.verify() }` near line 2437) runs on whatever slot the attempt took when it launched, so a cap lowered later only blocks new launches. Every build in the three cases goes through `Verification.verify()`, so one gate around those calls fixes all three cases and the m4-15 tracker gap for builds.

## Agent Brief

**Category:** bug
**Summary:** cap the verification builds and merge check builds that run at once with one in process FIFO build gate, read live from the workflow.

**Current behavior:**
- `agent.max_concurrent_agents` is checked only when an attempt launches (`SlotPlan.attempts`) and when a merge check starts (`SlotPlan.mergeCheckFits`). An attempt that already holds a slot runs `verification.verify()` whenever its agent submits, after a reload that lowers the cap and again on each resubmit after a killed or refuted build.
- On restart, `restoreWaiting` resumes every stored `verify` wait in the same tick through `resumeWait`, with no slot check. `slotUse()` does not count these reruns, so `syncMerges` and the attempt slot plan also start their work beside them. One run had four Gradle builds at once with the cap at 1.
- `TrackerSlots.runningTrackers(running.keys, ...)` also leaves out restored waits, so a tracker's limit can be exceeded the same way (m4-15 review).

**Desired behavior:**
- A `BuildGate` owned by the orchestrator. Every verification build and merge check build passes through it before it runs. First in, first out. Capacity is a lambda read on every admission, so a reload applies to builds that have not started yet. A build already running is never stopped.
- Capacity comes from a new optional key, `agent.max_concurrent_verifications`, a positive integer, falling back to `agent.max_concurrent_agents` when unset. A separate key because agent turns are mostly model time and run well in parallel while builds do not; the fallback keeps other workflows unchanged. A value that is not a positive integer fails preflight with `invalid_config`, like `max_concurrent_agents_by_tracker`.
- Through `buildGate.withBuild(context) { ... }`: the attempt's `verification.verify()` inside `waitingFor` near line 2437 (not the no check call at line 2431), the merge check's `verification.verify()` in the recheck near line 4804, and the restored rerun's `verification.verify()` in `resumeWait` near line 4969.
- Waiting in the gate can be cancelled; a cancelled waiter leaves the queue and takes no capacity. Capacity is released in a `finally`, on an exception or a cancellation too.
- At the start of each `dispatch`, call `buildGate.admit()`, so a reload that raised the capacity admits queued builds.
- A build that has to wait logs one INFO line with the issue context, such as `verification waits for a build slot (2 ahead)`. No new event type.
- Agent slot accounting does not change: restored waits still take no agent or tracker slot (bl-173). A merge check holds its agent slot while it waits in the gate; this cannot deadlock, since no build needs an agent slot to finish.

**Key interfaces:**
- `spec-core/src/main/kotlin/loop/core/orchestrator/BuildGate.kt` (new): `BuildGate(capacity: () -> Int)`, `suspend fun <T> withBuild(context: LogContext, block: suspend () -> T): T`, `fun admit()`.
- `Orchestrator.kt`: build the gate with `{ effective.config.agent.run { maxConcurrentVerifications ?: maxConcurrentAgents } }`, wrap the three call sites, call `admit()` in `dispatch`. Grep for the spots, never read the file whole.
- `spec-core/src/main/kotlin/loop/core/workflow/WorkflowConfig.kt`: `AgentConfig.maxConcurrentVerifications: Int? = null`.
- `spec-core/src/main/kotlin/loop/core/workflow/WorkflowFile.kt`: parse and validate the key next to `maxConcurrentAgents`.
- `SlotPlan.kt`: update the `SlotUse` and `SlotPlan` KDoc to point to the build gate.
- Docs: the slots bullet in `docs/self-hosting.md`, the defaults line and the merge check slot paragraph in `docs/spec-decisions.md`, and `CONTEXT.md` if it defines slots.

## Acceptance criteria

- [ ] `BuildGateTest`: with capacity 1, three concurrent `withBuild` calls run one at a time, in arrival order.
- [ ] `BuildGateTest`: lowering the capacity from 2 to 1 while two builds run admits no queued build until both have ended.
- [ ] `BuildGateTest`: raising the capacity, then calling `admit()`, starts a queued build.

- [ ] `OrchestratorRestartTest`: with three stored `verify` waits and `max_concurrent_agents: 1`, the fake check runner never sees more than one build at a time across the restored reruns, and all three finish in their stored order.
- [ ] An orchestrator test with `max_concurrent_agents: 2` and `max_concurrent_verifications: 1` has two attempts submit at once; their builds never overlap and both attempts finish.
- [ ] An orchestrator test lowers the cap with a reload while one attempt's build runs; a second attempt's build submitted afterwards starts only after the first ends.
- [ ] `MergeCheckOrchestratorTest`: a restored `verify` rerun and a merge check never build at the same time with capacity 1.
- [ ] Workflow config tests: an absent key falls back to `max_concurrent_agents`, `max_concurrent_verifications: 1` parses, and `0` or a non integer fails preflight with `invalid_config` naming the key.
- [ ] Existing `SlotPlanTest` and `TrackerSlotsOrchestratorTest` pass unchanged.
- [ ] `./gradlew build` passes.

## Out of scope

- Stopping or pre-empting builds already running when the cap is lowered.
- Counting restored waits against agent slots or per tracker limits (bl-173 keeps them slotless; the gate covers their builds).
- Sharing the build cap across projects through the machine slots in `<LOOP_HOME>/config.yaml`.
- Showing queued builds in `loop status` or recording a new event for them.
- Setting `max_concurrent_verifications` in Loop's own `WORKFLOW.md`; that is a human step after the build is installed.
- The test flakes under load (bl-07, bl-57, bl-183, bl-186).
