## What

M9's exit is "a merged retro proposal that measurably lowers cost, occupancy or refutations", and the plan never says how "measurably" is measured. Without it, neither a human nor the retro agent can claim that a change to a template, a verify contract or the config made Loop 20 percent cheaper or faster after a day, a week or a month. Most of this has to exist before M9, or the retro agent has nothing reliable to learn from.

Proposed shape, to settle in triage:

- **Metrics per delivered issue, not per attempt.** An attempt can look cheap and fail, which pushes the cost onto the next one. Measured from ready to delivered:
  - delivery rate: dispatched issues that end verified and delivered;
  - zero touch rate: delivered with no human touch;
  - cost per delivered issue: tokens and USD across every attempt of the issue, failed ones included;
  - lead time: wall time from ready to delivered;
  - first try verified: verified on the first submission, no refutation;
  - escape rate: delivered work that came back (reverted, reopened, changes requested in review). This is the guardrail that stops Loop from improving by cutting corners, with holdout failures and guard fires.
- **Attribution by config version.** Every attempt already records the config version (SHA of `WORKFLOW.md`) and the ledger row the template version, runner and model, so a change is a new config version and every result traces back to it.
- **Three comparison methods, strongest first:**
  1. Benchmark replay: a frozen set of 20 to 30 past issues, each with its base commit, checks and holdouts, run on the old and the new config, 3 times each since agents are not deterministic. The gate before a retro proposal merges. Distinct from M4's `loop replay`, which replays traces.
  2. A/B in production: Loop sends new issues at random to config A or B. Fair, needs volume.
  3. Before and after by config version over 7 or 30 days, split by kind. Cheap and muddied by backlog mix and model updates. Confirms, never decides.
- **Statistics.** Plan section 6.8 records a median of 5 to 18 million tokens per issue session and a 90th percentile of 45 to 50 million, so a "20 percent cheaper" from 5 issues is noise. Report ranges (confidence intervals), set a minimum sample (for example 20 issues per side), compare like with like (kind, number of criteria, diff size).
- **Every change carries an evaluation plan:** a hypothesis, the target metric and expected effect, guardrail metrics that must not get worse, the benchmark result before merge, production checks at 7 and 30 days, and a revert proposal if it is worse.

Missing today: an issue level rollup in the ledger (total cost and lead time across attempts), tracking after delivery (needs M4 reactions), difficulty signals, benchmark replay, and `loop report` comparing config versions with ranges.
