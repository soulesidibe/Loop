## What

Triage decides which are worth fixing; the mediums first.

1. **Medium. The wait ends before the agent has the prompt, so the answer can be lost** (`Orchestrator.kt`, around lines 2760 to 2761, `answered?.let { endWaiting(it) }` right after the render). Between the render and the first turn come `workspaceFacts`, `fillPrompt`, `recordPrompt`, `checkBudgets()` with `return budgetEnd(turns = 0)` (around line 2796) and `NetworkResume.open` (around line 2799). A breached issue or day budget parks the issue, or a session that fails to open fails the attempt, and the next attempt has `loop.answer` null since the wait row is deleted and `dispatchAnswers` is gone. The answer then exists only as a tracker comment the agent never reads. Fix: end the wait once the first turn started (or the runner accepted the prompt), or write the answered wait back on any failure before that. Test with a budget breach and with a failing session open right after an answer.
2. **Medium. `loop.answer` is opt in and Loop's own `WORKFLOW.md` does not read it**, so every answer is dropped on this repository while the wait ends and `loop answer` exits 0. Preflight renders the answer sample but does not warn when a template never reads `loop.answer`. `docs/PLAN.md` 8.9 has no `loop.answer` row and its `loop.retry_kind` row (around line 546) does not list `answer`. Fix: an `{% if loop.answer %}` block in `WORKFLOW.md` and any scaffold template (the `WORKFLOW.md` part is a protected file, a human step); a preflight warning, or append the answer when the template ignores it; the two PLAN table rows.
3. **Medium. For an issue of a non primary tracker the answer comment is never posted** (`AnswerCommand.kt`, around lines 53 and 99 to 107; `OpenProject.tracker()` builds `NamespacedTracker(primary, primary, ...)`). `loop answer local:x-1 "..."` finds the issue through the waiting records only, `addComment` returns `NotFound`, the command warns on stderr, exits 0 and says "Answered". The namespaced test (`AnswerCommandTest.kt`, around lines 237 to 256) never creates `x-1` and asserts no comment. Fix: build the tracker for the id's namespace, as `trackerPoll` does, and assert the comment with a real issue.
4. **Low. No size cap on the answer**; `PromptFill` never cuts `loop.answer`, so a huge answer can push the prompt over `promptLimit`.
5. **Low. A failed `endWaiting` after the render** is only logged; the next dispatch injects the same answer again. Harmless, undocumented.
6. **Low. A failed `question_answered` or `human_touch` record** after the answer transaction is a stderr warning with exit 0, so `loop trace` and the ledger can lack the answer. Both are separate writes.
7. **Low. `checkAsk` recognizes its own answer by `answered_at` equal to the local now**; two answers in one clock tick both report success. Practically unreachable.
8. **Low. An answer starting with `-`** is parsed by clikt as an option unless the operator writes `--`. Document it.
9. **Low. The `question` notice says `loop answer <issue>`** (`HumanChannel.kt`, around line 56) while the command also needs the text.
10. **Test gaps:** a human move against an answer at CLI level, the wait ending after render then a failure (1), a template without `loop.answer` (2), the comment on a namespaced issue (3).

Area: `AnswerCommand.kt`, `Orchestrator.kt` (grep, never read it whole), `Preflight.kt`, `PromptFill.kt`, `HumanChannel.kt`, `WORKFLOW.md`, `docs/PLAN.md`, `docs/spec-decisions.md`.
