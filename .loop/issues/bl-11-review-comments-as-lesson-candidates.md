## What

Plan 9.3 lists the sources of a lesson as an attempt, an answer or a retro. A human review comment is not one of them, though the `changes_requested` reaction (plan 6.7, M4) already sends it to the agent. The comment fixes one pull request and is then lost. The same remark has to be made again on the next issue in the same area.

Human review is the scarcest resource in Loop. A comment made once should become a standing rule when it is right.

Outside reference: Shopify's rebuild of its mobile app (shopify.engineering/shopify-app-rebuild, 2026-11-10) folds each day's review comments back into skills and its architecture doc, so a comment made once is not needed again.

Proposed shape, to settle in triage:

- A `changes_requested` comment creates a `candidate` lesson, with the comment as its `source` and the files the comment points at as its `area`.
- It never becomes `active` on its own: the human approves it with `loop lessons` (plan 9.3), or a later verified attempt in the same area confirms it, as for other candidates.
- Comments that are about this pull request only ("rename this variable") should not become lessons. Who filters them: the human at approval time, or a model at creation time?

This may end as an edit to the M6 part of `docs/PLAN.md` rather than code, since lessons land in M6.

## Questions for triage

- Is a review comment a lesson source in M6, or only after the retro agent in M9?
- Does every `changes_requested` comment create a candidate, or only those the human marks (for example a `lesson:` prefix)?
- Do review comments on the `files` tracker (comments under `## Comments` after a move back from `review`) count the same way?
