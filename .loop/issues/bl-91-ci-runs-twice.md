## What

Loop pushes the verified commit to `loop/<identifier>` when it opens or updates the pull request, which starts a CI run on a workflow triggered `on: push`. The merge check then merges the current base into the branch and pushes the merged head, which starts a second run, and `ci: actions` waits for that second one. The first run is spent minutes no gate reads. On Loop's own repository `build.yml` runs on every push and takes 12 to 16 minutes, so each issue costs about twice that; on a repository with a monthly Actions budget (the pilot app) it halves what the budget buys.

Possible directions for triage: push the merged head first when the base moved, so only one push happens; or document a workflow trigger that skips the first push (for example `pull_request` with a path or branch filter) and say which run the CI wait reads.

What the code does today, with `delivery.pull_request.merge`. An approved `Waiting(approval)` (by `loop approve`, or by `auto` itself under `policy: auto`) runs `PullRequestDelivery.deliver` with no handoff: it pushes V to `loop/<key>`, opens or updates the pull request and comments its URL. Then `Waiting(merge)` starts in phase `check`, and when it reaches the head of the delivery queue the check fetches the base. When the base is an ancestor of V the head stays V (outcome `up_to_date`) and nothing new is pushed, so that case already costs one push. Otherwise the check merges it into M and pushes M early (bl-174, `pushEarly` in the merge module), seconds after V.

The real cost, from `gh run list` on 2026-11-26: of 130 push runs on `loop/*` branches between 2026-11-24 23:00Z and 2026-11-26 20:27Z, 31 are runs of V cancelled 5 to 8 seconds in by the push of M (for example `loop/bl-191` at 15:55:42Z cancelled, M at 15:55:48Z green; `loop/m4-31` once ran 2.5 minutes before M cancelled it). Every pull request also starts a `pull_request` run that `build.yml` skips. So on Loop's own repository the concurrency group has already turned the second build into a cancelled one. The waste is still whole on a repository whose workflow has no such group, like the pilot app's, and Loop's saving rests on a file under `.github/` that Loop cannot check.

Direction chosen: with `merge`, the merge check owns the only push. An approved delivery no longer pushes or opens anything. It starts `Waiting(merge)` at once, holding no pull request number. When the check knows the head it will check (M after a merge, or V when the base is already in the branch), it pushes that head once and opens or updates the pull request and comments its URL right after, before the checks run, which is where bl-174 pushes M today. So each round pushes one head and starts one CI run, the one the CI wait reads, in both cases.

Why not the alternatives:

- A workflow trigger (only `pull_request`, or a filter): it edits `.github/`, a protected path, in every repository Loop delivers to, and only works where the operator does it. It stays a residual human step, not the fix.
- Merging the base at the approved delivery, before its push, and keeping the merge check where it is: it puts the merge outside the merge module and still pushes twice whenever the delivery waits in the queue and the base moves again before its turn.

What changes for a human. Under `policy: human` the approval is given on the evidence summary in the issue, before any pull request, today and after this change. Under `policy: auto` the auto merge gate decides after the check and the CI wait, so a result that falls back to `Waiting(approval)` still has its pull request open, at the checked head, when the human looks. A delivery queued behind another has no pull request until its turn. A conflict found by the merge check or by the early conflict check (bl-178) pushes nothing and opens nothing, so the comment names the branch and the base, not a pull request number. Without `merge` nothing changes: m2-25 pushes V and opens the pull request at once.

bl-97 stays separate. It changes when Loop counts its local merge check as enough proof and skips the CI wait, a policy decision with its own config, not a change of push order. Once this lands, its "first merged head" wording should read "the one head each round pushes". Its state stays `todo` with `deferred` until the maintainer schedules it.

## Agent Brief

**Category:** enhancement
**Summary:** with `delivery.pull_request.merge`, push one head per merge check round: the approved delivery stops pushing V, and the merge check pushes the head it checks once and opens or updates the pull request right after that push.

**Current behavior:**
With `merge`, the approved delivery calls `PullRequestDelivery.deliver` without a `Handoff`: the fingerprint check, the body, the lookup, the push of the verified commit V, the open or update of the pull request and the comment on the issue. Only then does `Waiting(merge)` start, holding the pull request number. The merge check looks the pull request up first and refuses the merge when none has the branch as head. In phase `check` it fetches the base, then either finds the base already in V (no new head) or merges it into a merge commit M, stores M as `candidate_head` and pushes it early (`candidate_pushed`). So when the base moved, `loop/<key>` gets two pushes seconds apart, and each push starts a GitHub Actions run on a workflow triggered `on: push`; the CI wait reads only the run of M.

**Desired behavior:**
1. **Approved delivery with `merge`.** It pushes nothing, opens nothing and comments nothing. It replaces the approved `Waiting(approval)` with `Waiting(merge)` in phase `check`, round 1, every key of the approval wait kept, the approval included, and no pull request number. A pull request URL the approval wait already holds (`commented`) is kept, so the comment is never made twice. The write that replaces the approval wait by the merge wait stays the conditional write of bl-250, so a `loop send-back` committed since the read still wins. Without `merge`, the m2-25 delivery is unchanged.
2. **The one push of a round.** In phase `check`, once the head to check is known (M after a clean merge, or V when the fetched base is an ancestor of V), and before any check runs, the merge check delivers that head through the existing `PullRequestDelivery` steps with no handoff, on the clean fingerprint of that head: the lookup, one unforced push to `loop/<key>`, the open or update of the pull request, and the comment, unless the wait already commented that URL. The wait stores the pull request number, the commented URL and, for M, `candidate_pushed` as today, so the push that starts the CI wait and the merge phase push again as a no op and record no second `branch_pushed`. This replaces the early push of bl-174 and keeps its order: M is stored as `candidate_head` before it is pushed.
3. **Failures of that delivery.** One that can be tried again (network, 5xx, a rate limit hold) ends the run with the wait kept in phase `check`, and the next run resumes on the head already made, with no second merge commit and no second fetch for M (the existing stopped check resume, base from `base_sha`). One refused for good is a merge step refused for good: `delivery_failed` with its step (`push`, `pull_request`, `comment`), back to an unapproved `Waiting(approval)` as other permanent merge failures do. This replaces today's never fatal early push (bl-174, bl-181): the push of a round now starts the pull request, so the check no longer goes on without it. `branch_push_failed` with `early` = `true` survives with its keys unchanged, so old traces still render: it is recorded only for a push step that can be tried again, before the run ends, and its meaning and human sentence change from "the merge commit is pushed after the checks" to "the push of the round failed and is tried again on the next run". A permanent push failure records `delivery_failed` only, not `branch_push_failed`.
4. **Lookup first, before a number exists.** While the wait holds no pull request number, a missing pull request is not a refusal, and a closed one or one merged at another commit is history, as `PullRequestDelivery` treats them. A pull request merged at the stored head or at the candidate head still counts as delivered. Once the wait holds a number, today's rules apply unchanged.
5. **No pull request yet in the texts.** The conflict, refuted and guard comments, the early conflict check's comment and any status or log line that prints the pull request number name the branch and the base instead when the wait holds no number, never `pull request #` with nothing after it. After an auto fallback, the new merge wait holds the commented URL but no number yet: its texts take the number from that URL, not from the branch name. A conflict pushes nothing.
6. **Queued waits.** A merge wait behind the head of the delivery queue holds no pull request until its own check. The early conflict check (bl-178) still runs from the local workspace, and the settle of a wait whose issue left the active states treats "no number and no pull request found" as a human move, not a refused merge.
7. **Old waits.** A `Waiting(merge)` written by the current binary (pull request number held, V already pushed) resumes and merges as today: the check pushes M once, or nothing new for V, and updates the open pull request.
8. **Docs** (files agents may edit): in `docs/spec-decisions.md`, the m2-26 "Handover from m2-25", "Lookup first" and phase `check` step 5 paragraphs and the m3-15 "Order" paragraph say that with `merge` the merge check makes the only push of a round and opens the pull request after it, with the bl-91 note on `build.yml`'s concurrency group rewritten as history, and the bl-181 paragraph and the `branch_push_failed` row of the event table say what the event now means. Also the matching sentences of `docs/plugins/tracker-github.md` (pull request delivery), `docs/self-hosting.md` (the delivery bullet) and the m2-25 and m2-26 paragraph of `docs/PLAN.md` section 6.5.
9. **Residual human step**, under `residual_human_steps`: none is needed for the fix. If the agent finds `build.yml`'s comments now say something false (they say a branch of this repository is built by its push), it proposes the exact new comment text there instead of editing `.github/`.

**Key interfaces:** `PullRequestDelivery.deliver` and `DeliveryFacts` (reused from the merge check, its step order and idempotence unchanged); the orchestrator's delivery of an approved wait (`deliverPullRequest`, `startMergeWait`) and `Wait.Approval.merging`; `Wait.Merge` (`pullRequestNumber`, `numberText`, `numbered`, `candidate`, `candidatePushed`, `pushedEarly`); the merge module's `runMergeCheck`, `checkPhase`, `pushEarly`, `resumeStopped`, `checkEarly`, `settleInactiveMerge`, `startCi`, `mergePhase`; `MergeCheck`'s comment texts; the `DeliveryExecutor` fakes of `MergeCheckOrchestratorTest.kt` and `CiWaitOrchestratorTest.kt`, and the loopback git server of `PullRequestDeliveryCommandTest.kt`. Tests that start from a wait already holding a pull request and must keep passing, adapted only where they build that wait: `MergeCheckOrchestratorTest`, `CiWaitOrchestratorTest`, `AutoMergeOrchestratorTest` and `BaseFetchOrchestratorTest` in `spec-core/src/test/kotlin/loop/core/orchestrator`; the four reaction tests `ApprovedGreenReactionTest`, `ChangesRequestedReactionTest`, `CiFailedReactionTest` and `MergeConflictReactionTest` in `spec-core/src/test/kotlin/loop/core/reactions`; `MergesTest` in `spec-core/src/test/kotlin/loop/core/merge`; `SendBackCommandTest` in `cli`. ## Out of scope

- Skipping or shortening the CI wait when the local merge check already passed on the same head (bl-97).
- Any change under `.github/` (protected), including the `build.yml` triggers and concurrency group.
- The m2-25 delivery without `merge`, which already pushes once.
- Draft pull requests, or opening the pull request before the merge check for visibility.
- A second push caused by a base that moves between the check and the merge (a new round, by design).
- Commit statuses instead of Actions runs (bl-60).
