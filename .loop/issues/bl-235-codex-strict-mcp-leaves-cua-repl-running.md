## What

On both `thread/start` and `thread/resume`, codex 0.167.0 started an MCP server, `cua_repl`, that `config/read` did not list, so the strict config could not disable it by name. Under `strict_mcp: true` the agent is meant to get no MCP server at all, so this weakens a guard.

The likely source is Codex's `computer_use` feature (`codex features list` shows it `stable`, `true` on the operator's machine), whose node REPL comes from the ChatGPT app. The thread config already turns the `apps` feature off under strict MCP; `computer_use` probably needs the same.

## Agent Brief

**Category:** bug
**Summary:** under `strict_mcp`, a Codex thread, started or resumed, runs with no MCP server, `cua_repl` included.

**Current behavior:**
Strict MCP disables, by name, each MCP server that `config/read` lists, and turns the `apps` feature off. `cua_repl` is not listed, so it still starts.

**Desired behavior:**
1. Under `strict_mcp`, the `config` of `thread/start` and of `thread/resume` also turns off the Codex feature that starts `cua_repl`, expected to be `computer_use`. Confirm the feature name against the pinned schema (`ComputerUseConfig` and the `computer_use` key) and with a real probe.
2. While probing, list every MCP server the thread reports and check none other is left, for example from the operator's enabled Codex plugins. Turn off any other built in source the same way, or record it in a comment when it cannot be turned off.
3. If no setting turns it off on the pinned version, the first turn of a strict session fails with `response_error` naming the server rather than run with it, and the docs say so.
4. Without `strict_mcp`, nothing changes.

**Key interfaces:**
- The thread `config` the Codex runner builds for `thread/start` and `thread/resume` under strict MCP.
- The strict MCP section of the runner's profile doc.

**Out of scope:**
- Updating the pinned Codex version.
- Changing the operator's own `~/.codex/config.toml`.
