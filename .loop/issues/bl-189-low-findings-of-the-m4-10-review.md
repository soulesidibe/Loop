## What

Low findings of the m4-10 review. Triage decides which are worth fixing.

1. **A failed waits read can end a drain early.** `Waits.read()` resets `stored` before filling it (`waiting/Waits.kt`, around lines 51 to 59), and `readWaits` in `Orchestrator.kt` lets the tick go on. `drainFacts()` then sees no waits, and since `RunDrain.remaining()` filters `facts.waits`, a running merge job is not counted either. One failed store read while only CI or merge waits remain records `run_drained` and exits 0. Running jobs still finish and the waits stay in the store for the next run, but the drain ends before its work. Suggested fix: count from `waits.busy`, or skip the drained check on a tick whose read failed. The same window exists on the first tick when the first dispatch returns early on a failed preflight, before waits are read.
2. **A restored verify wait gets no retry during a drain.** A verify wait restored from a previous process (`resumeWait`) is outside `executions`, so it is not in the drained set. Its failed rerun schedules no retry and the issue returns as a plain candidate, which a drain does not dispatch. It matches the criterion's wording, nothing is lost, and it is dispatched at the next `loop run`. Suggested fix: one line in the docs.
3. **An unreadable drain marker is not logged.** `drainRequested` in `RunFile.kt` catches `IOException` and returns false with no log line. A half written marker is read again at the next dispatch, so it is transient, but a lasting read error is silent.
4. **The marker is honoured in `--once` mode.** `tick()` calls `drain.notice`; the window is acquire to first dispatch since the marker needs the run id. Untested.
5. **`DRAINED` labels any normal return.** `RunCommand` sets `stopReason = DRAINED` after any normal return of `runUntilCancelled`. Correct today (the drain is its only return), fragile if another return is added.

Area: `RunDrain.kt`, `RunFile.kt`, `waiting/Waits.kt`, `Orchestrator.kt` (grep, never read it whole), `RunCommand.kt`.
