## What

Low findings of the m4-34 review. Triage decides which are worth fixing; 1 to 3 first, before m4-35 to m4-37 reuse the same path.

1. **The failure counter mark that bounds a reaction is in memory only** (`RetryCoordinator.kt`, the `reacted` set, around lines 94, 424, 512, 545 and 659). A restart between a reaction and its attempt's approval exit loses the mark, so `queue.drop(resetCounter = true)` zeroes the counter; a base that keeps moving plus a restart every cycle could exceed `max_attempts`. Derive the mark from the persisted retry error (`reaction`), or store it in the retry state.
2. **Several paths reset the counter without clearing `reacted`** (`fireDue` for parked issues, handoff, the `parkReason` path and `parkNow`, around lines 240, 430, 460 and 561). Conservative effect, an earlier park. Clear it in one helper around `queue.drop(resetCounter = true)`.
3. **The reaction ends the wait from the tick's snapshot** (`Orchestrator.kt`, around line 508, `Reactions.poll`). A `loop approve` or `loop send-back` landing while `poll` awaits GitHub is deleted with the wait, and the agent is retried on a slot. Re-read the wait just before ending it and skip when `approved` or `sentBack` is set. See bl-222 finding 2.
4. **Mergeability reads are sequential and inline in the tick**, no per tick cap; many watched pull requests and a slow GitHub delay every dispatch of the tick. Optionally bound the reads per tick.
5. **`MergeCheck.conflictFindings` says "verified and approved"**, wrong for a reaction on an unapproved wait. Reaction specific wording.
6. **`verifyFindings` is in memory only**, so a restart between the reaction and the retry leaves `retry_kind` = `reaction` with no findings in the prompt. Same as the merge check today, documented.
7. **Only unapproved `Waiting(approval)` is watched**, not every wait with a pull request number as the issue text says; spec-decisions states why. Note only.
8. **Test gaps:** a reload that adds or removes `reactions:`, and the restart cases of 1 and 6.
