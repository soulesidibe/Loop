## What

Found by the Fable 5.2 review of #45 (m2-11), confirmed by reading `bounceNotReady` (`spec-core/src/main/kotlin/loop/core/orchestrator/Orchestrator.kt:412`).

What is known:

- The comment and the label write are independent. If `addComment` fails and `updateLabels` succeeds, the issue carries `needs-info` with no explanation, and the label guard then suppresses the comment forever, restarts included.
- With a tracker whose label write fails every time (`Unsupported`, or a lasting error), the once rule lives only in the in memory `bounced` set, so every new process comments again. `loop run --once` under cron adds one comment per run. spec-decisions documents it, but it goes against acceptance row 1 of m2-11 for that setup.
- `bounced.retainAll(missing.keys)` forgets an issue that turns blocked for one tick, so a blocker that flaps comments again.
- Bounces run inline in `dispatch`, two tracker writes per issue, so turning on `ready:` over a large backlog makes one tick do 2N writes. Fine for the files tracker, worth a cap before a remote tracker.
- Related: once an issue gains its section, nothing removes `needs-info`, so the label stays on a dispatched issue.
- Review nit on the same area: `docs/spec-decisions.md` says the GitHub tracker runs the label contract tests, but no GitHub tracker exists yet, and the contract requires label writes that the API calls optional.

## Agent brief

**Category:** bug

**Summary:** The readiness bounce adds the `needs-info` label only after its comment was written, so an issue is never labelled without the explanation.

**Current behavior:**
For a candidate that fails the readiness check, the orchestrator writes a comment naming the missing sections, then adds the `needs-info` label, each write on its own. When the comment write fails and the label write succeeds, the issue carries the label with no comment. Every later tick and every later process sees the label and writes nothing, so the explanation never arrives.

**Desired behavior:**
- The label is added only when the comment write succeeded.
- When the comment write fails, no label write is attempted and the issue is not remembered as bounced, so a later tick tries the comment again. The failure is logged as today (`level=warn event=readiness outcome=failed` with the reason).
- When the comment succeeds and the label write fails, behavior stays as today: logged, and no second comment in the same process.
- An issue that already has the label still gets nothing.
- The spec decisions doc (readiness check, the bounce) states the new order and the retry after a failed comment.

**Key interfaces:**
- The orchestrator's readiness bounce and its in memory set of bounced issue ids.
- `TrackerAdapter.addComment` and `TrackerAdapter.updateLabels`.
- The events `issue_commented` and `issue_labeled` with `reason` = `not_ready`.

**Out of scope:**
- A durable record of the bounce for a tracker without labels.
- A cap on the bounces of one tick.
- Removing `needs-info` when the issue becomes ready.

**Triage notes:**
- Retrying the comment on every tick while the tracker keeps failing gives one warning per tick and per issue, which matches how other failed tracker writes are logged.
