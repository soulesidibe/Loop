What is known:

- The `move` and `comment` tool descriptions (`mcp/src/main/kotlin/loop/mcp/LoopMcpServer.kt`, `MOVE_DESCRIPTION`, around line 66) say "In Loop mode, end with submit_result" and "never move the issue yourself", while Loop's own `WORKFLOW.md` (lines 82 to 84) tells the agent to move to `review`. The agent cannot tell which mode it is in. One of Loop's own agents could call `submit_result` with status done, get `tool_request_failed` ("submit_result needs Loop mode") and waste a turn. A prompt line saying not to use `submit_result` here would close it.
- Call order over MCP is not guaranteed. `ToolMcpCommandTest` (`mcpCalls`, around line 241) was changed to wait for each reply, and `docs/spec-decisions.md` says Claude Code sends calls serially, an unverified assumption about a third party. A client that sends comment and move without waiting can get `issue_move_requested` first. Both still apply, only event order differs. A fair mutex in `ToolMcpCommand.call` would remove the dependency.
- The queue file name is `<epoch ms>-<pid>-<random>` (`spec-core/.../AttemptDirectory.kt`, around line 146). The CLI used one process per call, but over MCP the pid is constant, so two calls in the same millisecond order randomly.
- A comment over MCP has no size cap (`cli/src/main/kotlin/loop/cli/TrackerTools.kt`, around line 45). The CLI was bounded by argv and `submit_result` caps at 1 MiB, so an agent can queue a multi megabyte comment into the issue file.
- The empty comment refusal over MCP reads `... for example loop tool comment "..."` (`TrackerTools.kt`, around line 59), steering an MCP agent to the CLI. The server's own missing argument refusal (`LoopMcpServer.kt`, around line 129) lacks the `loop tool mcp:` prefix the other refusals carry.
- `ToolMcpCommand.call` (around line 96) catches only `ProgramResult`. Any other exception reaches the SDK without the "Nothing queued." wording. This already applied to `submit_result`.
- Test gaps: a non live attempt over MCP is tested only for the finished case (unknown attempt, other issue and other project only through the CLI); the drain's full redactor is not exercised over MCP.

## Agent brief

**Category:** bug

**Summary:** Tracker tools over MCP: refuse what cannot be applied at call time, cap the comment size, and make the order of queued requests the order of the calls.

**Current behavior:**
- A `submit_result` call in a project without Loop mode (no `kinds:` key in WORKFLOW.md) is queued and answered as queued. It fails only when the turn ends, as `tool_request_failed` with "submit_result needs Loop mode, a kinds: key in WORKFLOW.md". The `move` tool description tells the agent to end with `submit_result` in Loop mode, and the agent has no way to know which mode it is in.
- The MCP server handles calls concurrently. A client that sends `comment` then `move` without waiting for the first reply can get `issue_move_requested` recorded first, and two requests queued by one server process in the same millisecond are applied in random order, since the queue file name is `<epoch ms>-<pid>-<random>` and the pid is constant over MCP.
- A comment has no size limit over MCP or the command line. A comment larger than the tracker accepts is refused at the drain, after the turn, so a handoff can apply without its comment.
- The empty comment refusal over MCP tells the agent to use `loop tool comment "..."`. The server's own refusal of a missing or non string argument does not carry the `loop tool mcp:` prefix that the other refusals carry.
- A tool call that fails with anything other than a refusal (for example an I/O error on the queue) reaches the MCP SDK as a raw exception, without the "Nothing queued." ending.

**Desired behavior:**
- The tool config snapshot tells `loop tool mcp` whether the project runs in Loop mode. Outside Loop mode, a `submit_result` call is a tool error, returned in the same turn, that says the project has no Loop mode, tells the agent to move the issue with `move`, and ends with "Nothing queued.". Nothing is queued and no `result_requested` event is recorded. In Loop mode nothing changes. A snapshot written by an older Loop keeps working or is refused with the existing version message, never misread.
- The `move` and `submit_result` descriptions no longer contradict a prompt that tells the agent to move to `review`: they say that `submit_result` exists only in Loop mode and that the call itself says so otherwise.
- Calls of one `loop tool mcp` process are handled one at a time, in the order they arrived, and the requests they queue are applied in that order at the drain, also when two are queued in the same millisecond.
- A comment longer than 65,536 characters, counted as code points after redaction and trimming, is refused at once by `loop tool comment` (exit code of a rejected argument) and by the MCP `comment` tool (tool error). The refusal names the size and the limit and ends with "Nothing queued.". A comment of exactly 65,536 is queued. The cap is the same for every tracker and both ways of calling, and equals GitHub's own limit.
- The empty comment refusal over MCP names the `comment` tool and its `text` argument, not the command line. The command line wording is unchanged.
- The missing argument refusal reads like the other refusals of `loop tool mcp`, with the same prefix.
- Any exception in a tool call other than cancellation becomes a tool error whose text ends with "Nothing queued." when nothing was queued. No token or path the redactor would hide appears in it.

**Key interfaces:**
- `LoopMcpServer` (`SUBMIT_RESULT_DESCRIPTION`, `MOVE_DESCRIPTION`, the string tool helper and its missing argument reply).
- `ToolMcpCommand.call` and `ToolMcpCommand.submit`.
- `AttemptTool.queueMove`, `AttemptTool.queueComment`, `AttemptTool.refuse`, `AttemptTool.NOTHING_QUEUED`, `EMPTY_COMMENT`.
- `ToolRequestQueue.enqueue` and `ToolRequestQueue.pending` (file name order is the apply order).
- The tool config snapshot (`ToolConfig`, `ToolConfigSnapshotWriter`, `TOOL_CONFIG_VERSION`).
- `ToolRequest.Result`, and the drain's `applyQueuedResult`, which keeps its own refusal as a defence.

**Out of scope:**
- The agent facing prompt in WORKFLOW.md: the call time refusal replaces a prompt line, so the prompt stays as is.
- Cutting or splitting a long comment. It is refused, never cut.
- The GitHub tracker's own limit check at the drain, which stays.
- An operator MCP server (bl-44).
- The redactor test over MCP at the drain if it needs a new fixture: say so in the handoff comment instead.

**Triage notes:**
- Decisions taken: the comment cap is 65,536 characters counted as code points, and a `submit_result` call outside Loop mode is refused at call time instead of only fixing the prompt, because Loop's own workflow moves to Loop mode in M3 (m2-10) and a prompt line would then be wrong.
- The oversized comment lost with a handoff on the GitHub tracker (bl-48) is merged here: the cap lives in this brief. The cap in bl-29 for a `needs_info` summary uses the same number.
- The `blocked_by` entry m2-17 is done and holds nothing back.
