## Agent brief

**Category:** bug

**Summary:** Moving a waiting issue to another active state rejects the approval wait.

**Current behavior:**
An issue that waits for approval keeps waiting as long as its state is one of the active states. A human who moves it from `todo` to `in_progress`, or to any other active state, to say "not this result" leaves the wait in place. The issue is never dispatched, and a later `loop approve` delivers the old result against that intent. The only way to reject is a move out of the active states and back, on separate ticks.

**Desired behavior:**
- When the approval wait starts, Loop stores the issue's state at that moment in the wait data.
- On each tick, a wait whose issue reads active but in a state other than the stored one ends as a human move: the wait is removed, a `human_touch` of kind `move` is recorded with the two states, the log says the issue was moved by a human, and the issue is dispatchable again from the next tick. An approval already given for that wait is void and nothing is delivered.
- State names compare normalized, as elsewhere. A wait with no stored state (written by an older build) behaves as today.
- With pull request delivery, a wait in its merge phase follows the same rule before any merge call. An open pull request is left as it is.
- `loop approve` on an issue whose wait ended this way answers as for any issue that does not wait for approval.
- The same check runs for a restored approval wait after a restart.

**Key interfaces:**
- `WaitingIssue` data keys: a new key for the state at wait start, next to `TO`.
- The orchestrator's approval request and its per tick approval sync.
- `HumanTouch.MOVE`.

**Out of scope:**
- Label changes on a github issue that do not change its state as Loop reads it.
- Closing or commenting the pull request of a rejected wait.
- Atomic delivery with the wait row, the approve touch count, and the second result in one drain.

**Triage notes:**
- The `blocked_by` entry m2-24 is removed, m2-24 is done (merged in #63).
- The fingerprint never compared at delivery is overtaken: pull request delivery refuses a fingerprint that is not a clean commit and pushes that commit (m2-25), and the merge check compares the merged head with the verified fingerprint (m2-26). For a files tracker move it stays harmless.
- The note about raising bl-33's priority is obsolete, bl-33 merged in #68.
- The human touch items (the approve touch that no row counts, the false touch after a crash in `deliverApproved`) move to bl-64.
- Context from bl-54, not in scope here: a second pull request comment after a hard crash (the comment URL is stored on the wait only when delivery returns not delivered) and a failed `clearApproval` store write that leaves the wait approved. They belong to the same family as the items listed under out of scope: failed store writes and crash windows of the approval wait. They stay open as low notes in this file, not covered by the brief.
- Low items kept as notes, each needs a crash or a store failure at one exact point: the failed store write that leaves the wait as `verify`, the `claimsAnyId` case, one malformed file logging on each tick.
