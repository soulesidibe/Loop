## What happens

A `command` check passes or fails on exit code. A repository with existing lint or analyzer debt cannot add its analyzer as a check without fixing every finding first or keeping a baseline file by hand. So most projects leave static analysis out of their verify contract, and Loop verifies results that add new findings.

## Proposal

A check type, for example `{ type: ratchet, run: "<analyzer>", format: sarif }`, that runs the analyzer on the base commit and on the result, compares the findings, and refutes only on findings the result adds. The new findings go into `loop.verify_findings`.

## Open questions

- Which report formats to read first: SARIF covers detekt, Android lint and many others.
- How to match a finding across commits when lines move: rule, file and a hash of the surrounding code, rather than the line number.
- Whether to cache the base run per base commit, since the merge check reruns checks on current main.

## Acceptance criteria

- [ ] A result that adds a finding is refuted, with the finding in the evidence.
- [ ] A result on a base with existing findings, adding none, is verified.
- [ ] The check type is documented in `docs/PLAN.md` section 6.4 and `CONTEXT.md`.
