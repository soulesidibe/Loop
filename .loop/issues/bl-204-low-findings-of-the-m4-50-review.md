## What

Low findings of the m4-50 review. Triage decides which are worth fixing.

1. **A dead holder in another project keeps its lock.** At startup `freeProject` frees only the starting project's rows (`AbandonedAttempts.kt`, around lines 119 to 155; `ResourceQueue.freeProject`). Project A dies holding a lock (or dies queued, then gets the grant from a release elsewhere), and project B's agent polls `queued` until A's `loop run` starts again; with m4-26 the dead holder also counts against the machine wide limits. No later issue (m4-25 to m4-28, m4-51) plans a fix. Suggested fix, no schema change: a lock or queue row whose project has no live run file is freed with reason `abandoned`, on the tick of `loop run` and before a `request` answers `queued`, using `RunFiles(loopHome, projectId).peek(retry = false)` like `slotLive` in `StoreMachine.kt` (never peek the caller's own project, treat `Unreadable` as live). Acceptance: project A killed while holding, project B's queued request is granted without A restarting. Belongs in m4-25's area; triage decides whether to fold it into m4-25.
2. **A failed `freeAttempt` is never retried** (for example SQLITE_BUSY past the 5 s `busy_timeout`), logged once (`Orchestrator.kt`, around lines 1455 to 1457). The row stays while that run lives, and the project liveness check would not catch it. Retry on the tick, or sweep rows whose attempt is not running in this run.
3. **Design note for m4-25 and m4-26.** `ResourceQueue.settle` (around lines 104 to 118) grants the queue head at once on any free, and the attempt end free runs no provider `release`. m4-25 wants release marked, provider `release` on the tick, then the grant; m4-26 wants a request to stay queued under a limit or a dirty mark. Both will rework `settle` and the attempt end call.
4. **A grant to another project's request is recorded by the freeing process** with its own `runId` and through its own sink (`ResourceLocks.kt`, around lines 86 to 90 and 121 to 131).
5. **`recover(liveHolders)` uses a snapshot taken before the call** (`AbandonedAttempts.kt`, around lines 137 to 141). A lock another project's live run takes in between is unknown to the provider, which could delete its simulator. Matters with m4-27 and m4-28.
6. **A straggling `loop tool mcp` of an ended attempt can take a lock again after the free.** For m4-25.
7. **One corrupt row** (bad `prepared` JSON or timestamp) makes every lock change and `loop status` fail for the whole machine (`selectResourceRows`; `StatusCommand.kt`, around lines 76 to 81, exits with `EXIT_STORE`). Consider degrading status to a warning.
8. **Grant and release events are recorded after the commit** (`ResourceLocks.kt`, `change()`); a crash in between loses an event, the rows stay right.
9. **`freeAttempt` shares a try with `dropRequests` and `deleteDirectory`** (`Orchestrator.kt`, around lines 1452 to 1461). It returns a `Result`, so no leak today; its own try would be tidier.
10. **The downgrade consequence of schema 8 is written nowhere** in `docs/spec-decisions.md` (same gap bl-191 names for version 7). A revert can keep `SCHEMA_VERSION = 8` and the two tables, or reset `PRAGMA user_version = 7`. Note for bl-191: version 8 is now taken, so namespaced ids need 9.
11. **Test gaps:** the failure paths of `freeAbandonedLocks` (a failed free, a throwing `recover`, a failed provider load in `RunCommand.kt`, around lines 268 to 278), and a failed `freeAttempt` in the orchestrator.

Area: `ResourceQueue.kt`, `ResourceLocks.kt`, `AbandonedAttempts.kt`, `StoreMachine.kt`, `StatusCommand.kt`, `SqliteEventStore.kt`, `Orchestrator.kt` (grep, never read it whole).
