- Low to medium, security, first in line: the tree restore runs hooks and smudge filters configured from the agent's worktree on the host. `WorkspaceFingerprint.kt` (around line 101) runs `git restore --source=HEAD --staged --worktree` with only `core.fsmonitor=false` pinned. - Low, security: fingerprint and restore git have no timeout. `runGit` (around line 253) waits unbounded, so a filter that hangs blocks verification forever.
- Low, security, not reproduced: `HOME` is passed to the push (`GitPush.kt`, around line 211), and git's curl may read `~/.netrc`, so a host user's netrc entry for the GitHub host could authenticate the push instead of the delivery token. ## Agent brief

**Category:** bug

**Summary:** The delivery push and the base fetch must authenticate with the delivery token only, never with a `~/.netrc` entry of the host user.

**Current behavior:**
Every git process of pull request delivery gets a minimal environment that keeps the host user's `HOME`. The push and the fetch read no user or system git config, but git's HTTP transport may still read `HOME/.netrc`. A netrc entry for the GitHub host could authenticate a push or a fetch in place of the token of `delivery.pull_request.token`. Not reproduced.

**Desired behavior:**
- The git processes that talk to the remote (the push and the base fetch) run with a `HOME` that Loop owns and that holds no `.netrc`, or with netrc reading switched off in another way that holds for every supported git. The only credential git can find is the one Loop's credential helper answers for the configured host.
- A host user's `.netrc` with an entry for the remote host changes nothing: the server sees the delivery token, and with a wrong or missing delivery token the push fails as an authentication failure even when the netrc entry would have been accepted.
- Git processes that only read the project repository locally are not required to change.
- Nothing else of the minimal environment changes: `PATH` and the locale stay, no token variable reaches a process that does not need it.

**Key interfaces:**
- `GitPush` (the push, the fetch, `minimalEnv`, the settings for isolated processes, its temporary repository).
- `GitHubDelivery.push` and `GitHubDelivery.fetchBase`, unchanged for callers.

**Out of scope:**
- Filters and merge drivers from `.gitattributes`, and any same user threat (M5).
- The environment of workspace git commands (`WorkspaceGit`), which make no network call.
- Proxies and other curl settings.

**Triage notes:**
- Reduced to the netrc item. Priority lowered from 2 to 3, the first in line items are done.
- Done in m2-26, as the maintainer's earlier comment says: hooks off (`core.hooksPath=/dev/null`), `core.fsmonitor=false`, signing and gpg programs off, no automatic gc or maintenance, `--no-replace-objects`, a minimal environment and a 5 minute timeout, with the fingerprint going through `WorkspaceGit`. Items 1, 2 and 3 of the original list are closed.
- Carried to M5 planning, with bl-28 and bl-32: filters and merge drivers named by a tracked `.gitattributes` (no pin can switch filters off by name, so this needs the M5 sandbox or a fingerprint that does not run filters, a design choice), and the info items (the temporary repository's own config written between two processes, `rev-parse` in the project repository), which share the same threat of a hostile process of the same user.
