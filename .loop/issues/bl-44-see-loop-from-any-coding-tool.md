## What

Today Loop is seen through the CLI only: `loop status`, `loop trace`, `loop show`, `loop log`. The operator works inside AI coding tools (Claude Code, Codex, Cursor, Antigravity, T3 Code, VS Code, JetBrains IDEs) and wants to see what Loop is doing for them from wherever they are, with a UI as good as those tools have. It would also make Loop easy to show: Loop working inside Claude Code or Cursor says more than a CLI.

This fits the plan: no web dashboard in the core, and Symphony's HTTP API is a plugin (plan sections 1 and 10.4). Building one UI per tool would not scale, so the proposed shape, to settle in triage, is one read model and thin views:

- **One source of truth:** a local Loop API plugin serving the state that already exists in the store, the trace and the ledger (running attempts, waiting and parked issues with their reasons, verdicts and evidence, spend against budgets), plus a live event stream. Read only at first.
- **Views, in order of reach:**
  1. An operator MCP server, distinct from the agent facing one of m2-16 (`submit_result`), with read tools such as status, issue timeline and today's spend. One build reaches every MCP host. Where the host supports MCP Apps, it renders an interactive panel instead of text.
  2. A Claude Code status line: running, waiting for you, spend today.
  3. A VS Code extension (Cursor and Antigravity are VS Code forks) and a JetBrains plugin: a live board, the human log, verdicts.
  4. `loop watch`: a live view in the terminal, for servers and zero setup.
- Later, actions from the views (`loop resume`, `loop approve`, answering a `needs_info`), behind the same rules as the CLI. They meet the human channel of M4 and the remote channel of M8.
