## What

Human touches are spread over bl-31 (four findings, now canceled into this issue) and bl-42 (the approve touch that no row counts, the false touch after a crash). All come from one design: a touch is counted by the next attempt row of the issue, inferred at the next dispatch from the state of the last row. They should be one issue with one decision.

What is known:

- Duplicate touch after a hard kill or a failed row write: confirmed by logic. `recordReturn` reads the issue's last row and records a `move` when that row's state is not active, and nothing dedups against a touch already recorded, so a later attempt records the same human move again.
- Restored wait with no row: confirmed by logic. A restored wait (m2-04) can move the issue to review with no attempt and no row, so a later human return finds no row and records nothing.
- Loop's own move counted as a human touch: plausible. `issue_moved` is recorded after `tracker.moveIssue` returns, and a reconcile tick in between cancels the job so that close records a `human_touch` for Loop's own move. "Human wins" followed by a reconciliation stop for the same change may count twice. Any reconciliation stop counts as a `move`, including a label change, a blocker or a gone issue.
- Resume plus move counted twice: an issue parked while in a non active state and brought back with `loop resume` may count both a `resume` and a `move` touch (from the recheck of #54).
- From bl-42: the approve touch is rarely counted. `ApproveCommand` records the touch "counted by the next ledger row", and a delivered issue has no next row, so a delivered issue with no rework shows zero touches. And a crash or a failed store delete after `moveIssue` and before `endWaiting` in `deliverApproved` records a false `human_touch` move and no `issue_moved`.
- None of this was observed in practice: the store holds 7 `human_touch` events.
- bl-43 (measure whether a change improves Loop) and the m2-28 criterion "the ledger row shows zero human touches" both rest on this count.

## Triage notes

**What we have established**

- All the findings above stand by logic on main. The count today is inferred, not recorded: one `human_touch` event is written when a return is noticed, and the attempt row of the next attempt takes the count.
- bl-43 and m2-28 depend on the count, so it has to be settled before either is built. Priority 3 for now, since neither is scheduled before M4 or the workload exit.
- It becomes a ready-for-agent issue once questions 1 and 2 are answered: one issue "human touch accounting" that takes both plus the bl-42 items.

**Questions for the maintainer (drafted when bl-31 was triaged)**

1. Should touches be counted from the `human_touch` events of the issue since the previous attempt row, with one event per human action, instead of inferring a `move` from the last row's state at the next dispatch? That would settle the duplicate after a hard kill, the restored wait with no row, the resume plus move double count, and bl-42's approve touch that no row ever counts.
2. Should a delivery with no rework get its touches on a row at all? Today a delivered issue has no later row. Options: update the last attempt row at delivery, or add a per issue touch total that `loop report` reads.

**Also open from bl-31, not about touches, carried here so they are not lost**

3. For a turn with no `result` line (usage is in hand for a timeout after a `result` line, that part is bl-37): record the mid turn estimate as the turn's tokens, marked estimated, or keep null? Null is honest but hides the most expensive failures. The docs say the mid turn estimate is never recorded as usage.
4. Is a silent ledger file after the first warning acceptable, or should each run repeat the warning once per file? `HumanLogFile` reports the first failure only, by design in its KDoc, and the ledger file does not rotate.
