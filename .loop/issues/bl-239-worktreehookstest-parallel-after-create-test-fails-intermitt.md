The full build of bl-235 on 2026-11-26 failed once on `loop.cli.WorktreeHooksTest` test `after_create survives two parallel workspaces on a fresh repository`. Round 8, workspace p-2: the hook after_create failed with exit code 128, `fatal: failed to read .git/worktrees/p-1/commondir: Undefined error: 0`. Git seems to read the metadata of the worktree p-1 while the other hook is still creating it. Three reruns of `./gradlew :cli:test --tests 'loop.cli.WorktreeHooksTest' --rerun` right after passed. The bl-235 diff touches only the Codex runner and its docs, not `scripts/hooks/` or this test. The race is either in the documented hooks under `scripts/hooks/` (a protected path) or in git itself on macOS, and it can fail a merge check at random.

Bug, ready-for-human, priority 2. This issue now carries bl-57 (the same test, seen on Linux CI). A real race in the documented hook, not in the test: `git worktree add` writes `.git/worktrees/<name>/commondir` with a plain create, truncate and write, and git dies with "failed to read <path>" when that file exists but reads as 0 bytes (errno 0 prints as "Undefined error: 0" on macOS). So p-2's git (its `worktree prune`, its `worktree add`, which lists the other worktrees, or its `sparse-checkout set`) read p-1's commondir between create and write; git takes no lock on `.git/worktrees/` for readers. `scripts/hooks/worktree-after-create.sh` runs `worktree prune`, `worktree add` and `sparse_set` (around lines 63 to 81) with no lock between hooks, and `worktree-before-remove.sh` runs `worktree remove` and `worktree prune` the same way. Loop runs attempts in parallel against one repository, so this can fail a real attempt or merge check. bl-57's Linux failure fits the same unlocked section, or the shared config lock collision losing all 5 tries of `sparse_set`; one lock fixes both. Human lane: `scripts/` is protected under diff_policy, so an agent's diff would fail verification. The Gemini lane can take it. Cause found by reading git's behavior and the hook, not reproduced yet.

## Agent Brief

**Category:** bug
**Summary:** a lock around the shared git steps of the worktree hooks, so parallel `after_create` and `before_remove` hooks never read each other's half written worktree metadata.

**Current behavior:** two `after_create` hooks on one repository run `git worktree prune`, `git worktree add` and the first `sparse-checkout set` at the same time. Git can read another worktree's half written `commondir` and fail (exit 128). The first `sparse-checkout set` of each hook also collides on the shared config lock and gets past it only through 5 fixed retries. `before_remove` touches `.git/worktrees/` with no lock either.

**Desired behavior:**
- Each hook step that changes the shared repository (`worktree prune`, `worktree add`, `sparse_set` in `after_create`; `worktree remove` and `worktree prune` in `before_remove`) takes one lock in the repository's common git folder, for those steps only.
- A POSIX `mkdir` lock with the holder's PID written inside: wait with a time bound, take over a lock whose PID is dead, release on exit with a trap. A hook that cannot get the lock in time fails with a stderr line naming the lock and its holder.
- `read-tree` and other per worktree work stay outside the lock, so parallel checkouts still overlap. The 5 try retry in `sparse_set` may stay as a safety net, but the test must not depend on it.
- The scripts stay POSIX `sh`, safe to run again, and never reset or move a branch. `docs/workspaces.md` says how parallel hooks share the repository and drops "the script takes no lock".

**Key interfaces:** `scripts/hooks/worktree-after-create.sh`, `scripts/hooks/worktree-before-remove.sh`, `docs/workspaces.md`, `cli/src/test/kotlin/loop/cli/WorktreeHooksTest.kt` (`PARALLEL_ROUNDS`, now 10).

## Acceptance criteria

- [ ] The PR names the cause (an unlocked `worktree add` or `prune` reading another hook's half written `commondir`, plus the shared config lock) and adds the lock to both hooks.
- [ ] A stress script in the PR description (fresh repository, 4 hooks in parallel, 500 rounds, outside Gradle) reports its failure count before the change and 0 failures after it.
- [ ] `PARALLEL_ROUNDS` is at least 30, and `./gradlew :cli:test --tests 'loop.cli.WorktreeHooksTest' --rerun` passes 20 times in a row locally.
- [ ] `sh -n` passes on both changed scripts, and `docs/workspaces.md` describes the lock.
- [ ] `./gradlew build` passes.

Cause confirmed by a stress script outside Gradle (fresh repository, 4 after_create then 4 before_remove hooks in parallel, 500 rounds): 3 failures before, all `failed to read .git/worktrees/<name>/commondir`, and 354 sparse retries; 0 failures and 0 retries after.
