## What

When the app server of a Codex session exits, every later turn fails with `port_exit: the app server of this session is gone`, and Loop starts no second app server. After a network hold, the attempt starts over on a new thread. The Claude Code runner respawns a dead process with `--resume <runtime session id>` (m3-07) and resumes a held attempt's session (m4-46), so its work and context survive.

The pinned schema lists `thread/resume` (`plugins/runner-codex-app-server/schema/codex_app_server_protocol.schemas.json`). Use it:

1. A turn whose app server is gone starts a new app server, sends `thread/resume` with the thread id, and runs the turn on it.
2. `resumeSession` resumes the held attempt's thread at turn 1 when it was below the soft limit, as the Claude Code runner does.

First check with a real recording that `thread/resume` restores the thread on the pinned Codex version, including after the strict MCP config of `thread/start`.

## Agent Brief

**Category:** enhancement
**Summary:** the Codex runner resumes its thread with `thread/resume`, after its app server dies and after a network hold.

**Current behavior:**
A session runs every turn on one app server and one thread. When the app server exits, every later turn of the session fails with `port_exit: the app server of this session is gone`, and Loop starts no second app server. `CodexAppServerRunner` keeps the default `resumeSession`, null, so an attempt after a network hold starts a new thread with an empty history.

**Desired behavior:**
1. **Respawn:** a turn whose app server is gone starts a new app server with the same startup (`initialize`, `initialized`, `config/read` under `strict_mcp`), then sends `thread/resume` with the session's `threadId` instead of `thread/start`, with the same approval, sandbox, `cwd`, model and `config` (login shell off, strict MCP servers disabled, `apps` off, Loop's tools as `dynamicTools`) that `thread/start` sends. The turn then runs on the resumed thread. A respawn happens at most once per turn; a second exit in the same turn fails it with `port_exit` as today.
2. **After a network hold:** `resumeSession(ctx, runtimeSessionId)` returns a session that starts a new app server and resumes the thread of the earlier attempt with `thread/resume`, as the Claude Code runner does since m4-46. Loop's own rule decides when it is called (below the soft limit); the runner only implements it.
3. **Failure:** a `thread/resume` that fails (an error answer, a thread Codex cannot find, a response that does not match the pinned schema) fails the turn with `response_error` naming `thread/resume`, kills the app server, and never silently starts a new empty thread in its place.
4. The guards, the strict MCP settings and the holdout rules apply to a resumed thread exactly as to a started one.

**Key interfaces:**
- `AgentRunner.resumeSession(ctx, runtimeSessionId)`: implemented by the Codex runner; the runtime session id carries the thread id.
- `ThreadResumeParams` of the pinned schema (`threadId` required).
- The `continuation` capability row and the continuation section of the runner's profile doc.

**Acceptance criteria:**
- [ ] `./gradlew :plugins:runner-codex-app-server:test` passes, with fake app server tests for a respawn after an exit mid session, a resume after a hold, a failed `thread/resume`, and the strict MCP and `dynamicTools` settings on the resume request.
- [ ] `AgentRunnerContract` passes for the Codex runner with `resumeSession` overridden.
- [ ] `docs/plugins/runner-codex-app-server.md` and `docs/spec-decisions.md` describe the respawn and the resume.
- [ ] One real Codex run on the pinned version confirms a resumed thread keeps its history, written up in a comment (judgment call).

**Out of scope:**
- Updating the pinned Codex version or regenerating the schema.
- Resume by history or by path; only by `threadId`.
- Changing when Loop calls `resumeSession` (the m4-46 soft limit rule).
