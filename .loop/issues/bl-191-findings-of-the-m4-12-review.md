## What

Triage decides which are worth fixing.

1. **Medium. The schema version does not mark namespaced ids.** Since m4-12 every new event, attempt, ledger, claim, wait and park row carries `default:<id>`, while `SCHEMA_VERSION` stays 7 (`SqliteEventStore.kt`, around line 709). The store already refuses a newer version (around lines 1048 to 1056), so a bump to 8 with no DDL would make a downgrade fail loudly. Today an older binary opens the store silently and reads `default:<id>` as a native id: its waits and claims are orphaned, ledger and trace by bare id miss the new rows. Suggested fix: bump to 8, and write the downgrade consequence in `docs/spec-decisions.md` "Namespaced issue ids" (it is written nowhere).
2. **Low. A bare id with a colon reads as namespaced.** `NamespacedId.parse` and `read` (`NamespacedId.kt`, around lines 35 and 47) read a pre m4-12 bare id like `abc:def` as tracker `abc`. GitHub and files ids never hit this.
3. **Low. `AttemptTool` opens the store with `AS_STORED`.** `AttemptTool.kt` (around line 96). Safe today since it reads by attempt id only; a future read by issue there would miss namespaced rows.
4. **Low. Two single row reads have no order.** `SELECT_PARKED_ONE` and `SELECT_WAITING_ONE` match `IN (?, ?)` with no ordering; both forms can coexist only after a downgrade.
5. **Low. Changing `tracker.id` orphans rows.** A `tracker.id` changed after namespaced rows exist reads `default:<id>` rows as a foreign tracker. Untested and undocumented.
6. **Low. Doc drift.** PLAN (around line 871) says the primary keeps bare ids, but new primary rows are `default:<id>`, and logs and events of a single tracker project show `default:<id>` until m4-47.
7. **Low. Machine wide reads mislabel other projects.** `toLedgerRow` for `SELECT_MACHINE_ATTEMPTS_SINCE` labels other projects' bare rows with the opening project's primary id. Cosmetic.

Area: `SqliteEventStore.kt`, `NamespacedId.kt`, `AttemptTool.kt`, `docs/spec-decisions.md`, `docs/PLAN.md`.

## Agent Brief

**Category:** bug
**Summary:** the docs still say a manual schema rollback is safe, which no longer holds since namespaced ids, and no test pins the refusal of a newer store.

**Current behavior:** `SCHEMA_VERSION` is 10 and `checkedVersion` in `SqliteEventStore.kt` refuses a store whose `user_version` is higher, so an unaided older build already fails loudly. `docs/self-hosting.md` Known limits tells the operator to roll back by setting `user_version` back by hand and says every migration only adds tables and indexes. Done to a store written by m4-12 or later, that rollback lets a build before m4-12 read `default:<id>` rows as native ids, silently. `docs/spec-decisions.md` "Namespaced issue ids (extension, m4-12)" does not record this. No test covers the refusal of a newer version.

**Desired behavior:** decided, no schema bump and no migration; the existing refusal stays as it is.
1. `docs/self-hosting.md` Known limits keeps the manual rollback note and adds the limit: a store written by m4-12 or later holds namespaced ids (`<tracker id>:<native id>`); setting its version back by hand to run a build before m4-12 makes that build misread those rows (waits and claims orphaned, ledger and trace by bare id missing them), so never roll back across m4-12 on a store that has run since. The safe way is to move the store file aside so the old build starts with a fresh store. Rolling back between builds at or after m4-12 stays as documented, with today's numbers: 7 for a build between m4-12 and m4-50, 8 before m4-25, 9 before m4-26.
2. `docs/spec-decisions.md` "Namespaced issue ids (extension, m4-12)" gets one bullet, "The downgrade": m4-12 did not bump the schema version, m4-50 bumped it to 8 the next day, so a build before m4-50 refuses a store opened by a later build; setting the version back by hand to a build before m4-12 misreads namespaced rows, as in the self hosting known limits (link it).
3. A store test where a store whose `user_version` is `SCHEMA_VERSION + 1` is refused with `StoreError.Unavailable`, its message naming both versions. A store is never written with a version higher than the build's own, so this is how a reader with an older constant is checked.

**Key interfaces:** `store/src/main/kotlin/loop/store/SqliteEventStore.kt` (`SCHEMA_VERSION`, `migrate`, `checkedVersion`, read only here); a store test under `store/src/test/kotlin/loop/store/` (next to `SqliteResourceLocksTest.kt`, which already sets `user_version` by hand); `docs/self-hosting.md` (Known limits); `docs/spec-decisions.md` ("Namespaced issue ids (extension, m4-12)").
