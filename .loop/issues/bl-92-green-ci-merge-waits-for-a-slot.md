## What

Since m3-15 the CI poll of a merge wait runs in the tick with no slot. Once CI is green, the merge phase (the auto merge gate, the risk reviewer and the merge) starts in `syncMerges` only when `running + merge checks < max_concurrent_agents`. While a wait sits in its CI phase, its slot is free, so the dispatch of the same tick gives it to a new attempt.

Seen: bl-39's CI went green at 21:42 UTC, but bl-85 and m3-16 had taken both slots at 21:29, when bl-86 merged. bl-39's verified, CI green pull request waits for one of those attempts to end, which can take an hour or more. The longer it waits, the more likely main moves and the merge check and its CI wait run again.

Possible directions for triage: let the merge phase after green CI run without a slot, like the CI poll (it runs a read only reviewer and API calls, no agent and no build); or reserve a slot for a merge wait in its CI phase, so dispatch does not fill it. bl-86's slot plan owns the capacity rule, so the fix lands in that plan.

## Acceptance criteria

- [ ] `./gradlew --no-daemon build` passes.
- [ ] A merge wait whose CI went green starts its merge phase without waiting for a slot taken by an attempt dispatched during its CI phase. Either the merge phase runs with no slot, or a slot is reserved for the wait.
- [ ] A slot plan test reproduces the seen case: two slots, a merge wait goes green while two attempts run, and the merge phase starts in the next tick.
- [ ] The choice between the two directions is written in the commit message. Judgment call.
