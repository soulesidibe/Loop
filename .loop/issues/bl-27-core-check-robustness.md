## What

What is known:

- Confirmed by reading: `file_matches` runs the regex on an agent controlled file of up to 16 MiB with no time or stack limit (`CoreChecks.kt` around lines 65 and 194). Nested quantifiers can hang the io thread and cancel does not interrupt `find`. A pattern like `(a|b)*` on long input throws StackOverflowError, an Error that `timed` (catches Exception) and the orchestrator (catches CancellationException) let escape.
- Confirmed: `guards: ~` parses as no guards (`WorkflowFile.kt` around line 357), while `kinds: ~` is rejected. That breaks the "a guard is never silently off" rule.
- Confirmed: globs that can never match pass validation: `./scripts/`, `/` alone, `..` segments, `!x`, `[abc]` taken literally.
- Plausible: git runs blocking inside `withContext(io)`, so a cancel waits up to 120 s per git command and the process is not destroyed on interrupt; `out.get()` has no timeout if a git child keeps stdout open.
- Plausible: a `guards.base` starting with `-` reaches git as an option. The base is local `main`, which can be stale against a workspace cut from a newer commit.
- Test gaps: no worktree based test, nested repo or ignored file, type change or unmerged status, git timeout, pathological `file_matches` input, `guards: ~`.

## Agent brief

**Category:** bug

**Summary:** Refuse guards config that silently does nothing, and bound the time of a `file_matches` pattern.

**Current behavior:**
`kinds.code.verify.guards: ~` loads as no guards, while a null `kinds` or `holdout` is `invalid_config`. A `guards.base` that starts with `-` is accepted and reaches git as an option. Globs that can never match pass validation: a `..` or `.` segment, `/` alone, a leading `./`, a leading `!`. A `file_matches` pattern with nested quantifiers can run without limit on a file of up to 16 MiB, and a cancel does not stop it.

**Desired behavior:**
- `guards: ~` (the key present with a null value) is `invalid_config` with the message `kinds.code.verify.guards must be a map`, like a list value today. An absent key still means no guards.
- `guards.base` that starts with `-` is `invalid_config`, the message naming the key.
- For each glob of `guards.protect`, and of the test globs of `guards.languages` if they share the parser: a leading `./` is dropped like a leading `/`. A glob that is empty after that, or holds a `.` or `..` segment, or starts with `!`, is `invalid_config`, the message naming the key and the glob.
- Brackets stay literal. The spec decisions doc says so in the guards paragraph.
- A `file_matches` match runs under a deadline of 10 seconds, the same mechanism the deny guards use. Past it the check could not run, with a reason such as `the pattern did not finish in 10 s on <path>`. It never reads as failed and never hangs the verification.

**Key interfaces:**
- The workflow parser's guards section (`GuardsConfig`, `WorkflowError.InvalidConfig`).
- `CoreChecks.fileMatches` and the deadline watched character sequence of `DenyGuards`, which can be shared.
- `CheckResult.startError` for the could not run reason.

**Out of scope:**
- Pinning the base commit (bl-32) and the stale local `main` (bl-59).
- Making git calls inside `diff_policy` cancellable.
- Character class support in globs.

**Triage notes:**
- Trimmed to the four live items. The 10 second pattern deadline is accepted.
- Obsolete: the `StackOverflowError` escape. `CoreChecks.timed` now catches `Throwable` and reports could not run.
- Wontfix: `[abc]` taken literally. Paths such as `app/[id]/page.tsx` are real, so a literal bracket is the safer reading. The docs say so in one sentence.
- Moved: the stale local `main` as base is bl-59.
- Kept as a low note, not in scope: git cancel latency and `out.get()` without a timeout. `CoreChecks` git has its own 120 s wait and `destroyForcibly`, so the latency is real but bounded.
- Dropped: the test gaps on worktrees, nested repositories and type changes. m2-13 and m2-26 added most of them.
