## What

Low findings left after the m4-22 fix. Triage decides which are worth fixing.

1. **The once only post guard is in memory and keyed by attempt.** A crash, or a later attempt, can post the same deliverable again (`Orchestrator.kt`, `postedDeliverables`, around line 561 and 4456 to 4470).
2. **An `unknown` fingerprint weakens that guard.** The key is `issue/attempt/fingerprint` (around line 4486). With the fingerprint unknown twice, a failed move and a changed file in between, a second verification is seen as already posted and, under auto, moved with the earlier comment. Skip the guard when the fingerprint is `unknown`.
3. **The files tracker drops blank lines and trailing spaces in a comment** (`FilesTracker.kt`, around lines 409 to 414), so a posted markdown file reads with its paragraphs merged on the files tracker. No forging is possible.
4. **Files already in the workspace pass the deliverable gate** and are posted as the verified deliverable (m4-21 carry over, also bl-201 finding 1).
5. **The auto fallback's policy is reported two ways.** The summary says "The delivery policy is auto" while the `approval_requested` event records `policy: human` (around line 4410). Cosmetic.
6. **With a null `attemptId`, `postSummary` returns silently** (around line 4534, older behaviour), so the fallback and failure notes are not shown in that edge case. The wait and the deliverable are correct.
7. **A key stays in `postedDeliverables`** when an auto move never succeeds in that attempt. A few strings, memory only.
8. **Test gaps:** no orchestrator level test for the human path of a second submitted result, or for a restored wait with a null attempt id.
9. **A secret the redactor does not know**, written by the agent into a deliverable, is published on the tracker before any human reads it, under both policies. By design; worth a doc line.

Area: `AttachDelivery.kt`, `EvidenceSummary.kt`, `FilesTracker.kt`, `Orchestrator.kt` (grep, never read it whole).
