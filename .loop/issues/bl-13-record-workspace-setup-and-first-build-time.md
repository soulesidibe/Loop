## What

Nobody knows how long an attempt spends before the agent does useful work: workspace creation, `after_create` and `before_run` hooks, and the first build. bl-01 gave each attempt its own Gradle daemon pool, which adds a cold daemon start to every first build. The pilot app (iOS, the M2 workload) will have much longer first builds than Loop.

Before deciding whether Loop needs warm workspaces (prepared checkouts with caches built, claimed at dispatch), the cost has to be measured.

Outside reference: Shopify's remote dev environments (shopify.engineering/remote-dev, 2026-10-22) cut setup from over 30 minutes to a few minutes with a warm pool of machines, destroyed after each session. Their agent's share of merged mobile PRs went from 6% to 61% over the same period.

Proposed shape, to settle in triage:

- The ledger row per attempt (m2-19) gets the `PreparingWorkspace` duration, hooks included.
- The first build time is harder: Loop does not know which command is "the build". Options: the duration of the first run of the kind's first visible check, or a hook that reports it.
- `loop report` shows the median of each per project.
- No warming design in this issue. The decision comes after about a week of data.

## Triage notes

**What we have established**

- Setup time can be derived from events today. There is no duration on the `PreparingWorkspace` phase, but its event is recorded after workspace creation, `after_create` and `before_run` have all finished, so its timestamp minus the timestamp of `attempt_started` is the setup time. Each hook also records its own `duration_ms` on `hook_finished`, and each check records `duration_ms` on `check_finished`.
- The ledger question is moot, m2-19 is done. The ledger attempt row holds the wall time of the whole attempt and no setup figure. `loop report` does not exist, the plan puts it in M4.
- So the week of data before deciding on warm workspaces can be read from the event store with a query, with no code change.

**Questions for the maintainer**

1. Is a query over the events enough for a week of data on the pilot app (setup time from `attempt_started` to the `PreparingWorkspace` event, hook durations from `hook_finished`, first check duration from the first `check_finished` of the attempt)? If yes, this closes as wontfix for now and reopens only if the numbers call for warm workspaces.
2. If a ledger column is wanted anyway: is "first build time" the duration of the first run of the kind's first visible check? That is the only definition Loop can compute without a new hook, and it says nothing for a kind whose first check is not a build.
