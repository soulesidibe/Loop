## What

- **Moved base in the merge phase.** A run started in phase merge that finds a moved base now stops at phase check of the new round (`Merges.kt` around line 249) and rechecks at the next tick, once an agent slot is free. Under `loop run --once` the invocation ends there instead of running the check in the same run. The spec decision says so, the pull request body did not.
- **Two paths without a test of their own.** Nothing asserts that a run started in phase check keeps its agent slot through the merge under `ci: none` (`waits.checks` stays 1), and nothing covers the start in phase merge after `retrying()`. Both are simple by reading (`CiWaitOrchestratorTest`, `MergeCheckOrchestratorTest`).
- **The auto merge reviewer is outside the agent cap.** The review gate's model session runs with no agent slot, bounded by the machine slot and the one head queue (`Orchestrator.kt` around line 4806). This is what bl-173 asked for, but `agent.max_concurrent_agents` is no longer a ceiling on every model session, and with no machine cap only the queue bounds it. Worth a sentence in the docs.
- **Readability.** The "Slot" paragraph of m2-26 in `docs/spec-decisions.md` is very long, and its first sentence ("It holds an agent slot... like an attempt") reads as unconditional until the bl-173 text qualifies it.
- **Older, made rarer by bl-173.** In `syncMerges` the machine slot is claimed before a lazy `scope.async`. If the scope is already cancelled when `job.start()` runs, the body and its `finally` never run, so the machine slot row and the `checking` entry stay until the pid liveness rule clears the row after the process exits.
