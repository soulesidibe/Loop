## What

What is known:

- Medium, a rate limit hold between the add and the removal costs a whole attempt (around lines 227 to 231, `send` around 292 and 305). If the POST of the handoff label spends the last request (`x-ratelimit-remaining: 0`), the DELETE is refused locally. The issue keeps both labels and stays eligible, the refresh also fails, and the attempt ends as a counted `refresh_error` failure. After the reset, a full new attempt runs only to repeat the move. This matches the triage decision (add first, then remove) but is untested.
- Medium to low, a second removal failing leaves a silent handoff (around line 229). With two required labels, if the first DELETE succeeds and the second fails, the move reports failure and no `issue_moved` is recorded, yet the issue has already left the active set. The attempt ends `not_eligible` with counters kept. `docs/plugins/tracker-github.md` (partial failure, "the issue is still eligible") and `docs/spec-decisions.md` are wrong for this case.
- Test gaps: partial failure is tested only with one required label and a 403 on the removal. There is no test with two required labels or with a rate limit hold between the add and the removal.

Questions for triage:

- Should a move whose add succeeded but whose removal is held or fails be retried at the next tick, instead of costing an attempt?
- Should any removal that took the issue out of the active set count as the handoff, with `issue_moved` recorded?

## Triage notes

**What we have established**

- The code is unchanged since #65: `GitHubTracker.moveIssue` calls `updateLabels(add = [handoff label], remove = required)`, which sends one POST then one DELETE per required label and stops at the first failure. Tests cover one required label with a 403 on the removal only (`GitHubWritesTest`, "a failure after the add fails the move, and the next move repeats both calls").
- `docs/plugins/tracker-github.md` ("Partial failure") and the spec decisions doc (m2-23, "Order and partial failure") both say "the issue stays eligible". That is false once one of two required labels was removed, because `isEligible` needs every required label. The docs are wrong today for two required labels, whatever the answer below.
- Both findings are real, but both fixes change what a handoff is, so the maintainer must choose. The two missing tests (two required labels, a hold between the add and a removal) should be written against the chosen behaviour.
- Priority stays 2. It would be 3 unless the pilot app runs near its rate limit or with two required labels. The rate limit case needs the POST to spend the last of 5,000 requests.

**Questions for the maintainer**

1. Should the handoff label win on read? That is, an issue that carries a handoff label (`needs-review`, `needs-info` or the configured ones) is never a candidate, whatever its required labels. Then the single POST is the whole handoff, atomic, and the removals become cleanup that may fail or be held without cost. It closes the rate limit case, the two label case and the reload race of bl-48 in one rule. The price: the documented return path changes. Today "an issue sent back with it still on is eligible again"; with this rule the human must remove `needs-review` to send an issue back. The reviewer's recommendation is yes: the smallest code change (a read side filter plus docs) and it removes the whole class.
2. If not, should a move whose add succeeded but whose removal was held by the rate limit be finished by Loop at a later tick instead of costing an attempt? That needs a stored "handoff pending" fact per issue (a new waiting reason or a row), since an in memory note is lost at a restart.
3. Should a move that removed at least one required label, so the issue already left the active set, be recorded as `issue_moved` (with a note that a label is left) instead of as a failure with no event?
4. How likely is the two required labels case for the M2 workload? The pilot app and the playground use one (`ready-for-agent`). If one label is the only supported shape for now, preflight could refuse or warn on more than one for the github tracker and the second finding disappears.
