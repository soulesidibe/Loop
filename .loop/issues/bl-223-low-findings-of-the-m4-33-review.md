## What

Low findings of the m4-33 review. Triage decides which are worth fixing; 1 and 2 first.

1. **An unclosed code fence in the agent's body makes the follow up uncommentable.** `FilesTracker.createIssue` reads back only id, title, state and labels, so a body with an odd number of fence lines is written; later `addComment` returns `Malformed` because `insertComment` finds the footer inside an open fence. Dry run `insertComment` in the read back and reject, or close an open fence before the footer.
2. **A failed parent comment after a successful filing is reported as a failed follow up** (`Orchestrator.applyFollowup`, `return applyComment(...)`), so the agent is told it failed and files the same issue again. Record the comment failure as `request=comment` naming the filed id, and return success for the follow up.
3. **The tool's limit check is not atomic** (`FileFollowupTool.kt`: count, enqueue, record), so parallel calls can all be told `queued` and the extras fail at the drain. The bound holds; only the answer misleads. Record before counting, or serialize per attempt.
4. **No size cap on title or body at the tool**; GitHub rejects a title over 256 characters or a body over 65,536 only at the drain, after a slot is used. Cap both in the tool as structured failures, and collapse the title to one line.
5. **`"$prefix-%02d".format(...)` uses the default locale** (`FilesTracker.createIssue`); use `Locale.ROOT`. Fails safe.
6. **Docs:** say that a follow up is held from dispatch by `required_labels` (or `needs-triage` not being an active label), not by the tool.
7. **GitHub body text can @mention people or cross link issues**, as `comment` already can. No fix needed unless wanted.
