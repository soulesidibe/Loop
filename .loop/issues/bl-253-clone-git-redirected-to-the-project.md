## What

Loop's own git, run in a clone workspace, reads where the repository is from files inside the clone's `.git`, which the agent owns. Three shapes of that folder send Loop's git to the operator's project instead of the clone.

1. **`commondir` and links in `.git`.** A `.git/commondir` file naming the project's `.git` (the alternates left as they are) still passes `WorkspaceClones.state` as a clone. Reuse then lists the project's remotes and removes them from the project, with the project's remote tracking refs. `writeBase` writes `refs/loop/base/<base>` in the project, and the merge check's `git merge` moves whatever project branch the clone's `HEAD` names. A symbolic link at `.git/config`, `.git/refs` or `.git/packed-refs` pointing into the project does the same, since git writes through it.
2. **`extensions.refStorage`.** With `core.repositoryformatversion=1` and `extensions.refStorage=files://<project>/.git` in the clone's `.git/config` (no `commondir`, no link), every ref read and write goes to the project, even with the environment pins below: `update-ref refs/loop/base/main` wrote in the project, `HEAD` was read from the project, and the merge check's `git merge` moved the project's `main` (`fatal: bad object main` afterwards).
3. **`core.worktree`.** `core.worktree=<project>` in the clone's config (or in `config.worktree` with `extensions.worktreeConfig`) makes the project's folder the work tree of every git Loop runs in the clone. The merge check's `git merge` and its abort then write the operator's files, and `status`, `ls-files`, `diff` read the project's files instead of the clone's, so the fingerprint, the session brief and the workspace facts describe the wrong tree. `-c core.worktree=<clone>` does not override it.

### Current behavior

- `WorkspaceClones.state` accepts any `.git` folder whose `objects/info/alternates` names the project's object folder. It never looks at `commondir`, at links inside `.git`, at hard linked files or at `extensions.refStorage`.
- `state` runs only at prepare (reuse), before `writeBase` and before the import. Every other git Loop runs in the workspace after the agent's turns (fingerprint, workspace facts, session brief, merge check, `AutoMergeGate` diffs) runs with no check of the clone's layout.
- `WorkspaceGit` starts git with `-C <workspace>` and the minimal environment, which drops every `GIT_` variable. Git finds the repository, the work tree and the common folder from the clone's own files.

### Desired behavior

1. **Layout check.** A clone workspace is refused unless its `.git` is a real folder (not a link, not a file), holds no `commondir` entry of any type, holds no symbolic link at its top level or anywhere under `refs/` and `logs/`, holds no regular file at the top level of `.git` or under `logs/` with a link count above one (`unix:nlink`), and whose `.git/config`, read with `git config --file <clone>/.git/config --get-all extensions.refstorage` run outside the workspace, holds no value containing `://`. This is besides the alternates rule of today. `WorkspaceClones.state` makes this check and returns `Foreign` with a reason that names the offending path or key, so reuse fails the Attempt with it and the import and `writeBase` skip or refuse as they do for any `Foreign` state today. Symbolic links under `.git/objects/` are deliberately allowed: they can only add objects to what the clone sees and what Loop writes there, which is harmless to the project.
2. **Checked at every use, not only at prepare.** The agent can change its `.git` between prepare and verification, so the same check runs right before every git process `WorkspaceGit` starts in a clone workspace (or once right before each Loop operation in it, with no agent turn in between). A failed check runs no git and fails the call with the named reason, which every caller already treats as a failed git call (the merge check ends as a failed check).
3. **Environment pins.** Every git process `WorkspaceGit` starts in a clone workspace has, in its environment, `GIT_DIR=<workspace>/.git`, `GIT_COMMON_DIR=<workspace>/.git` and `GIT_WORK_TREE=<workspace>`, real paths, set after any caller supplied variable so no caller can change them, together with bl-246's `GIT_NO_LAZY_FETCH=1` (same builder, no conflict: all of them are set after the extras). An optional fourth pin, `GIT_REFERENCE_BACKEND=<format>://<clone>/.git`, also overrode a hostile `extensions.refStorage` in the replay and stopped the `commondir` ref write, but it is version dependent and is never relied on alone: the layout check stays the guard. Callers that pass `-C` may keep doing so. With `GIT_WORK_TREE` pinned, the `--show-toplevel` guards (`WorkspaceFingerprint.kt` around 150, `SessionBrief.kt` around 118, `WorkspaceFacts.kt` around 85, and `CoreChecks.kt` around 244 for bl-254) always pass in clone mode. They stay as they are for `hooks` mode, so keep them.
4. **Why both.** The pins alone are not enough: git's ref store reads the `commondir` file itself and ignores `GIT_COMMON_DIR`, and `extensions.refStorage` with a `files://` path sends the ref store to that path whatever the three pins say, so refs are still read and written in the project (replayed below). The `extensions.refstorage` read is run with `git config --file` outside the workspace so the hostile config never decides where that read itself goes. The layout check alone is not enough: `core.worktree` is config the agent can set at any time, through includes too, and only `GIT_WORK_TREE` (or `--work-tree`) wins over it.
5. **What is not pinned.** Git Loop runs in the project (the project steps of `WorkspaceClones`, `git clone` among them, the replay sites, `GitPush`) and in the import's temporary repository (run with `--git-dir`) keeps today's environment. `git clone` run with `GIT_DIR` and `GIT_WORK_TREE` in its environment fails (replayed below), so the project calls must never get the pins. The steps `create` runs in the new clone it built (`remote remove`, `config`, `checkout`) may get them; they must keep working.
6. **Mode from the workflow.** The check and the pins apply when `workflow.workspaceGit` is `Clone`, decided by the workflow, never by what `.git` looks like. In clone mode a `.git` that is a file, a link or missing at any use after prepare is a refusal. `hooks` mode keeps today's behavior whatever its `.git` is. Pinning a linked worktree is possible (`GIT_DIR` would be the `gitdir:` target, `GIT_COMMON_DIR` the project's `.git`, and the replay shows that stops a `config.worktree` redirect), but a worktree shares the project's config, refs and hooks, so the agent already reaches the project through git itself. That is the gap clones close, and pins add nothing until worktree mode isolates.
7. **Docs** (files agents may edit). `docs/workspaces.md`, clone section: the layout Loop requires of a clone's `.git` (folder, no `commondir`, no link at the top level or under `refs/` and `logs/`, no hard linked file at the top level or under `logs/`, no `extensions.refStorage` naming a path), that it is checked before every git Loop runs in the clone, that Loop pins `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE` to the clone, and in the threat model paragraph that this closes the path through Loop's own git while writes by absolute path and the agent's build code stay open until M5. The reuse paragraph of the usage list names the new refusal reasons. `docs/spec-decisions.md`, section "Clone workspaces (extension, bl-28)": the same two rules in one or two sentences each.

### Test recipes (replayed on git 2.54)

- **Links in `.git`:** replace `<clone>/.git/config`, `<clone>/.git/refs` or `<clone>/.git/packed-refs` (after `git pack-refs --all` in the project) with a symbolic link to the project's same entry. Proof: an unguarded `remote remove origin`, `update-ref refs/loop/base/main HEAD` or `update-ref -d refs/remotes/origin/main` changes the project.
- **Hostile `extensions.refStorage`:** in the clone, `git config --file <clone>/.git/config core.repositoryformatversion 1` and `git config --file <clone>/.git/config extensions.refStorage files://<project>/.git`. Proof the setup is live: with the three pins, `update-ref refs/loop/base/main HEAD` in the clone writes the ref in the project, and with `HEAD` at `refs/heads/main` an unguarded merge moves the project's `main`. Optional: show that `GIT_REFERENCE_BACKEND=files://<clone>/.git` overrides it on this git version.
- **Hard links in `.git`:** after a merge check that stopped on a conflict, hard link `<clone>/.git/MERGE_MSG` and `<clone>/.git/MERGE_MODE` to files in the project (for example new files under the project's `.git`). Proof: an unguarded merge rewrites the project files in place. Config, refs, the index and `packed-refs` are written by lock and rename, so a hard link there is broken, not written through.
- **Hostile `core.worktree`:** `git -C <clone> config core.worktree <project>`, and a second variant with `extensions.worktreeConfig=true` and `git config --worktree core.worktree <project>`. For the merge check, make a base commit on a project branch that is not checked out (adding a new file `h.txt`). - **Replaced `.git`:** after reuse, replace `<clone>/.git` with a file holding `gitdir: <project>/.git`, and in a second case remove it. Without the fix, git in the clone finds the project's repository (through the `gitdir:` file, or by walking up to the project when `.git` is missing and the workspace root sits inside the project).
- **Unchanged project:** compare the project's `.git/config`, `packed-refs` and `git for-each-ref` output byte for byte, and for the work tree the file listing with content hashes, the `.git/index` hash and `git status --porcelain`, before and after.
