## Agent brief

**Category:** bug

**Summary:** A failing test on CI prints why it failed, and two parallel `after_create` hooks on a fresh repository no longer collide on the shared git config as a matter of course.

**Current behavior:**
- When a test fails on CI, the log shows the test name and `AssertionFailedError at File.kt:line`, never the assertion message, the cause or the output the `fail(...)` call was written to print. No test report is kept. Flakes seen once (bl-15, bl-57, bl-62, and a `GitPushTest` timeout test) could not be diagnosed.
- On a repository without `extensions.worktreeConfig`, two `after_create` hooks that run at once collide on the lock of the shared git config in about 9 runs out of 10: the first `git sparse-checkout set` of each writes that setting. The hook retries up to 5 times, 0.2 s apart, and fails with git's error after the last try. `WorktreeHooksTest`, "after_create survives two parallel workspaces on a fresh repository", failed once on CI in its `fail(...)` branch.

**Desired behavior:**
- For every Gradle test task of the build, a failed test prints its exception message, its causes and a stack trace in the build output, on CI and locally. Passing tests print as today.
- The parallel hooks reach the config write in a way that does not depend on winning a 1 second race: either the shared setting is written once before the per worktree work, serialized between hooks, or the retry is bounded by time rather than by 5 fixed tries and only retries the lock error. Whichever is chosen, a hook still fails with git's own error and exit code when the failure is not the lock.
- A hook that gives up says, on stderr, how many tries it made and the last git error, so the test's failure message names the cause.
- The scripts stay POSIX `sh`, safe to run again, and never reset or move an existing branch.

**Key interfaces:**
- The shared Gradle convention that configures `Test` tasks (`testLogging`).
- The `after_create` worktree hook script and its `sparse_set` function, and the `before_run` hook if it shares the pattern.
- `WorktreeHooksTest` and its `PARALLEL_ROUNDS`.

**Out of scope:**
- Uploading test reports as a CI artifact. It needs a pinned action sha that an agent cannot look up, a human can add it.
- The 60 s stalls of test JVMs under load (bl-07) and the reconciliation flake (bl-15).
- The `ToolMcpCommandTest` flake itself (bl-62, merged into this issue): this issue only makes its next failure readable.

**Triage notes:**
- Rescoped by the reviewer to "CI shows why a test failed", plus a hook test that no longer depends on the race.
- bl-62 is merged into this issue. When `ToolMcpCommandTest` fails again with its message visible, refile it with the message. If the message shows a server that was alive and silent for 60 s, it belongs with bl-07, not with the MCP code.
- The issue text says the hook output is in the CI log of run 43555877652. It is not: the log holds only the assertion error type and line. The test task logs events only, with no exception message, and the workflow uploads no test report.

The retry path is the normal path, and the test relies on it. Two hypotheses fit a loaded Linux runner, neither proven: all 5 tries lose the lock, or the hook passes the test's 30 s hook timeout while the runner stalls.
- Run 43555877652 had three attempts. Attempt 1 failed on `GitPushTest`, which is filed in bl-63.
